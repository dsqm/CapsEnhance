# CapsEnhance

把 **CapsLock（大写键）** 改造成一个"增强修饰键"的 Windows 快捷键增强程序。

按住 **C** 进入映射模式，此时右手的常用键被映射为光标移动 / 编辑动作，配合 **D**（增益）和 **F**（Shift）可更高效地操作文本，并支持智能"按词跳转"。

- 纯 C 实现，底层键盘钩子，无第三方依赖，便携单文件。
- 常驻系统托盘，随时可暂停 / 退出。

---

## 一、快捷键

### 主映射键

| 按键 | 作用 |
| ---- | ---- |
| **C**（CapsLock） | 按住进入映射模式，下列"触发键"按映射动作生效；映射期间本程序自身的触发全部被屏蔽 |
| **D** 或 **左 Alt** | 增益：点按动作时自动"补齐到 3 次连续动作"（重复节奏）。两者完全等价，`Caps+Alt+…` 即 `Caps+D+…` |
| **F** | Shift：动作期间按住 Shift，产生位移/选中 |
| **\`**（C 按住时） | 开始 / 结束日志记录（诊断），见"日志与诊断" |

> C 单独按住不放 = 不做任何事（进入映射模式）；不触发真实 CapsLock。

### 逐格输出的打断

词跳距离小（<6 字符）或程序不支持置位时，动作为**逐格发送方向键**（大距离可能持续数百毫秒）。期间随时可以打断，打断后光标停在**已到达的位置**、Shift 选区保留已扩部分：

- **松开 C**：立即停止（映射模式结束）
- **按下其他触发键（改道）**：立即停止当前输出，改道动作随后自动开火——例如正在逐格输出 `←` 时按 `C+L`，左移立即停止并开始向右跳

### 触发键 → 动作

| 触发键 | 动作 |
| ------ | ---- |
| `I` | ↑ 上箭头 |
| `J` | ← 左箭头 |
| `K` | ↓ 下箭头 |
| `L` | → 右箭头 |
| `P` | Home |
| `;`（OEM_1） | End |
| `R` | Backspace |
| `W` | Delete |
| `Space` | Enter |
| `Tab` | 真实 CapsLock 切换 |
| `N` | 词跳 向左（WordJump left） |
| `M` | 词跳 向右（WordJump right） |

> 修饰组合示例：
> - `C + J` = 左箭头；`C + D + J` = 连续 3 次左箭头；
> - `C + F + J` = Shift + 左箭头；`C + D + F + J` = 连续 3 次 Shift + 左箭头；
> - `C + Alt + J` = `C + D + J`（左 Alt 即增益）。Alt 在映射期间被完全屏蔽，不会触发菜单栏。

## 二、词跳（WordJump）规则

`N` / `M` 不做简单的 "Ctrl+方向"，而是**读取控件真实文本**，按自定义边界算法跳到目标位置，因此在中文、英文、数字、生僻字混排文本里表现更稳定。

### 字符分类

每个字符被归为一类，**连续同类字符串视为"一个词"**：

| 类别 | 说明 |
| ---- | ---- |
| `CH_OTHER` | 剩余的"其他"字符：汉字、其他语言文字、生僻字、emoji 等 |
| `CH_ALPHA` | 字母 + 数字（含全角 `Ａ-Ｚ`/`ａ-ｚ`/`０-９`）——同一组，`21M` 是一个词 |
| `CH_HANGUL` | 谚文（韩文）自成一组：`U+1100-11FF` / `U+3130-318F` / `U+A960-A97F` / `U+AC00-D7FF` |
| `CH_SEP` | 分隔符：空白 + 标点（ASCII / 全角 / CJK 标点） |

分类采用**反向判定**：先枚举字母数字 / 符号归入对应类，剩下的全部归 `CH_OTHER`——因此汉字等其他语言文字无需逐个枚举码位，天然连成一类。

### 跳转语义

- 左右跳都在"词的边界"处停（类型切换处）。
- **默认不跨行**：分隔符串只在行内跨（空格/制表），`\r`/`\n` 不跨——行首右跳停在本行行尾，行中左跳停在本行词首。
- **只有出发点已在行尾/行首才跨行**：行尾右跳 → 下一行行首词（跳过缩进）；行首左跳 → 上一行行尾词（跳过行尾空格）；相邻空行会被跳过。
- 例子 `你好，世界1234abcd中国` → 跳转停在：`你好，|世界|1234abcd|中国`。
- **代理对（补充平面字符，如扩展G区生僻字）当作一个字符整体**，不会拆散。
- 光标落在代理对中间这类异常位置会被归一。

### 文本读取通道（按优先级尝试）

读不到文本、或读回的文本被判定为占位时，自动沿下一个通道继续；**全部失败**才发原生 `Ctrl(+Shift)+方向键`。各通道有各自的体量上限，超过即视为"本通道不可用"，继续往下试：

| 通道 | 体量上限 | 超过上限时 |
| ---- | -------- | ---------- |
| 经典 Edit / RichEdit / EmEditorView | **64000 字符** | 放弃本通道：`EM_GETSEL` 把选区起止打包进返回值的 `LOWORD`/`HIWORD`，**每端只有 16 位**，更长的文档读回的光标会回绕成错位值（宁可退回也不能算错位置） |
| Scintilla 系 | **2 MB**（文档字节数） | 放弃本通道：不为巨型文件开跨进程读缓冲 |
| UIA / IA2 | 读回文本 **< 2 字符**即视为占位假文本 | 放弃本通道 |
| 原生 `Ctrl+方向` | —— | 兜底，不再往下 |

> 实测（真实 `Edit` 控件，逐档试）：1000 / 30000 / 63000 / **64000** 字符都走经典 Edit 通道；**64001 字符起 Edit / Scintilla / UIA / IA2 四路全部失败，直接落到原生 `Ctrl+方向`**。也就是说经典 Edit 控件既没有 UIA 也没有 IA2 文本，超限就是一步退到底，不会"降级到 UIA 慢慢跳"。

1. **经典 Edit / RichEdit / EmEditorView**：`WM_GETTEXT` + `EM_GETSEL`。白名单外不放行（Chromium 系窗口对这两条消息回的是标题和垃圾值）；直接置位后回读校验，控件只实现半套协议时自动退回逐格箭头。
2. **Scintilla 系**（Notepad3 / Notepad++ / SciTE）：`SCI_*` 窗口消息。文档以字节为单位（UTF-8 下中文 3 字节/字），整条通道在字节域取原始文本再转成 UTF-16 交给词边界算法；`SCI_GETTEXT` 的缓冲区指针属于对方进程，必须先 `VirtualAllocEx` 再读回（直传本地指针会读崩对方）。跳距 ≥ 6 时用 `SCI_SETSEL` 瞬跳（置位后回读校验，不符则退回逐格箭头）。
3. **UIA（UI Automation）** `TextPattern`/`TextPattern2`：支持 QQ、Edge 等 Chromium/WinUI 控件。锚定顺序：焦点元素沿祖先链 → 焦点 HWND 沿祖先链 → 焦点 HWND 子树检索（焦点有时落在没有 `DocumentRange` 的 Pane 上，必须往下找）。**读回的文本短于 2 字符时视为占位假文本弃用**。
   - **Electron 类编辑器**：其无障碍节点（`role=textbox` 的 div）只有在 开启无障碍模式（或系统检测到读屏器）时才写入光标附近的真实文本并同步选区——未开启时会主动把节点内容清空，因此外部读到的是 1 字符占位。**开启该项后，词跳引擎（含中文混排、不跨行规则）即可完整工作**；未开启则走原生 `Ctrl+方向` 兜底，或通过配置文件把该程序加入原生词跳名单。平滑光标一类只影响视觉动画，与此无关。
4. **IAccessible2** (`IAccessibleText`)：其余无障碍文本控件（同样弃用短于 2 字符的占位读回）。
   UIA / IA2 跳完会**回读校验**：仍是同一页文本（长度与内容一致，坐标可比）时按差值补发一轮；偏差超过原步数说明该程序文本坐标与实际光标位置系统性不符（渲染装饰、折叠语法被光标整块跳过，表现为短跳准、长跳超调），**本次放弃补正，不做任何自动切换**——这类请把进程名加入配置名单。
5. 全失败则原生 `Ctrl(+Shift)+方向键` 兜底 —— **Ctrl 必须真的按住**（在方向键之前按下、之后抬起），否则目标收到的只是单格方向键。由目标程序自身的词导航完成按词跳转。

> 跨进程消息坑：`SendMessageTimeout` 的返回值只表示"是否发送成功"，窗口过程的返回值必须通过最后一个参数 `lpdwResult` 取。传 `NULL` 的话拿到的是恒为 1 的状态值 —— 曾导致 `WM_GETTEXTLENGTH` 恒等于 1、文本永远只读到一个字符，词边界算法整个失效。

### 直接置光标（远跳提速）

跳转距离 ≥ 6 个字符时**直接置位**（瞬跳），不再逐格发送方向键；小距离仍发真实方向键保持行为一致。置位后回读校验，控件不配合就退回逐格箭头。三条置位路径：

| 通道 | API | 依据 |
| ---- | ---- | ---- |
| 经典 Edit / EmEditorView | `EM_SETSEL` | 经典编辑协议（无 anchor 概念，Shift 位移按"向左锚右端 / 向右锚左端"给出有序选区） |
| Scintilla | `SCI_SETSEL(anchor, caret)` | wParam=锚、lParam=活动光标，天然支持选区位移 |
| **UIA** | `TextRange.Select()` | 官方语义：退化（空）range 上调用 Select 时 *"the text insertion point moves to the starting endpoint"*——即直接移动光标。**Chromium 系对折叠 range 的负向端点移动一律拒绝**（实测 moved=0，"N 不行 M 可以"），因此向左目标用"Start 从文档头正向数 + End 绝对定位回 caret"构造，全程只用正向增量与绝对定位；带 Shift 保留展开区间产生选区 |
| **IA2** | `setCaretOffset` / `setSelection` | IAccessible2 规范：*"Sets the position of the caret"*，不支持时返回 `E_FAIL` 退回箭头 |

- UIA/IA2 的直接置位**仅限无 Shift**：带选区时读回的位置是选区起点而非活动端，目标计算不成立，置位会产生错误选区——Shift 位移走箭头（anchor 语义天然正确）。
- **置位并非对所有 UIA 实现有效**：Chromium 系（QQ/Edge/Electron）支持（但只支持移动 End 端点，向左需全正向构造）；**WPF 系（如 Quicker 的文本框）的 `Select()` 会返回成功但选区不动** —— 它还会让显示光标短暂闪到目标位置却不真正生效，所以连续两次判定无效后，本次会话内不再对该程序尝试置位（消除闪烁，重启程序恢复；日志会写明）——回读校验发现"光标未动"后自动退回箭头，功能正确只是逐格偏慢；嫌慢可把该程序加入 `[NativeWordJump]`。
- UIA/IA2 置位的回读校验比经典 Edit 更严：置位后重新读文本+光标，**仍是同一页文本且光标恰在目标**才算成功；HRESULT 成功但回读不符时，不叠加箭头（避免双重错误），本次到此为止（诊断日志会记录）。
- 三个通道置位后都会让视口跟随：Edit 发 `EM_SCROLLCARET`、Scintilla 发 `SCI_SCROLLCARET`、UIA 调 `ScrollIntoView`——否则光标会被移到窗口外看不到。

两个实测坑：
- EmEditor 的 `WM_GETTEXT` 返回计数把结尾 NUL 也算进去（比 `WM_GETTEXTLENGTH` 多 1），多出的 `'\0'` 会被当成一个分隔符字符参与跳词、算出越界目标——已剥掉。
- EmEditor 会在直接置位后吞掉第一支方向键（逐格跳少走一格）——经典 Edit 通道能读回光标，跳完按差值**自校验补发**（只补一轮，带 Shift 的选区不补）。

## 二点五、配置文件（CapsEnhance.ini）

与 exe 同目录，首次运行自动生成带注释的模板；**改动后需重启程序生效**（或用托盘"重启程序"）。

格式（INI 风格，零依赖）：`;` 或 `#` 开头的行是注释，空行忽略，`[段名]` 行用于切段。

```ini
[General]
; 以管理员身份运行：启用后启动时自动申请管理员权限（会弹 UAC）
; 只认 0/1：1=启用，0=禁用（其它写法一律视为 0）
RunAsAdmin = 0
; 日志文件大小上限（KB）：超过后保留最近的一半内容，0 = 不限制
LogMaxKB = 2048

[NativeWordJump]
; 命中名单的程序：Caps+N / Caps+M 不做文本探测
; 直接发送 Ctrl+← / Ctrl+→，由程序自身的词导航完成按词跳转（Shift 位移同样支持）
; 每行一个进程名：完全匹配、大小写不敏感、.exe 后缀可写可不写
; Editor.exe
; SomeApp
```

- **`RunAsAdmin`**：启用后双击启动即以管理员身份运行（自动弹 UAC）。只申请一次——已提权的实例不会重复申请；用户取消 UAC 时按普通权限继续运行，不会循环重启。
- **`LogMaxKB`**：日志（`CapsEnhance.log`）大小上限，默认 2048 KB。超过时保留最近的一半内容并留下一行 `----- 日志已达上限 -----` 标记，避免长期开着记录涨到几十 MB；填 `0` 表示不限制。
- **`MaxArrowSteps` / `OverStepMode`**：控制逐格词跳（小距离或程序不支持置位时）的最大步数（按字符数，粗略值）。**达到**阈值的逐格跳转按 `OverStepMode` 处理（判定在发送方向键处，补正等所有路径同样受约束）：`0` = 只发送**一个方向键**（跳一格即停）；`1` = 改发 **Ctrl+方向键**（由目标程序自己的词导航完成，瞬时）。`MaxArrowSteps = 0` 表示不限制（与旧逻辑一致，逐格发完）。瞬跳路径（经典 Edit/Scintilla/UIA 置位）不受影响。无论配置多少，单次逐格发送另有 **256 步的硬上限**（防误配导致无限发送）。
- **`[NativeWordJump]`**：适用于编辑器文本读不到，或**读到的文本坐标与实际光标位置不符**（跳词超调、光标乱飘）的程序——这类程序的光标会整块跳过渲染装饰，按文本算出的步数发箭头必然偏。
- **托盘提示会标注真实运行权限**：按进程令牌检测（不是照抄配置值），以管理员运行时提示形如 `CapsEnhance：正在映射（管理员）`——配置与实际不一致时以此为准。

## 三、架构

```
       底层键盘钩子                        主线程（消息窗口）
   ┌──────────────────┐   PostMessage   ┌──────────────────────────┐
   │ hook.c           │ ───────────────▶ │ main.c                   │
   │  LowLevelProc    │   WM_CAPS_*      │  窗口消息循环 + 和弦引擎   │
   │  · 捕获 C/触发  │   WM_TRIG_*      │  · 计时器 → 开火/重复     │
   │  · 维护 D/F 门闩 │────────────────▶ │  · ActPost() 投递动作     │
   │  · 屏蔽无效按键  │────────────────▶ │  · 托盘 / 暂停 / 日志      │
   └──────────────────┘   WM_PROBE/TOGGLE└────────────┬─────────────┘
                                                      │ ActJob（FIFO + 开火快照）
                                                      ▼
                                               ┌──────────────────┐
                                               │ act.c  执行线程   │
                                               │  会阻塞的发送动作  │
                                               │  在这里串行执行    │
                                               └────────┬─────────┘
                                                        │ NavJump() / SendActOnce()
                                                        ▼
                                               ┌──────────────────┐
                                               │ nav.c   send.c   │
                                               │  词跳：读取文本通道│ 模拟按键：扩展键
                                               │  + 边界算法       │ 标志/逐条节奏/
                                               │  + 诊断(NavProbe) │ Ctrl·Shift 组合
                                               └──────────────────┘
```

### 为什么会有 act.c（执行线程）

**`WH_KEYBOARD_LL` 的回调在"安装它的线程"上执行**，而钩子是由主线程安装的
（`dwThreadId = 0` 只表示"全局钩子"，不表示"系统线程"）。一次词跳在主线程上
可能连续阻塞数百毫秒：逐格方向键最多 256 步 × ~13ms、`SendNativeWordJump`
四个 40ms 组合间隔、`NavJump` 的跨进程同步 IPC（`SMTO_BLOCK`，单次最长 300ms）、
UIA 的 COM 往返。**主线程被占住的这段时间，系统级键盘输入无法被钩子处理** ——
表现为全局输入卡顿；超过 `LowLevelHooksTimeout` 钩子还会被系统静默摘除，
CapsEnhance 就此"莫名其妙失效"却没有任何日志。

所以主线程只维护和弦引擎状态（稳定期、重复节奏、动作栈），把"真正会阻塞的
发送动作"整体投递到执行线程串行执行。投递项自带开火快照（D/F 修饰与已发送
次数），执行线程不回头读主线程的 volatile 状态，两边只通过队列通信；队列是
FIFO，"先开火、后补齐"的顺序语义与原同步执行完全一致。

两个由此而来的约束值得记住：

- **`ActInFlight()` 门控**：同一时刻只让一发动作在飞。这正是原来同步执行时的
  天然限速（主线程被占住时定时器根本跑不了）；少了它，长按词跳键会在队列里
  堆出一串尾流，松手后还在跳。
- **`ActClearKeepFill()`**：引擎复位时丢掉未开始的"重复开火"，但保留"松手
  补齐" —— 后者是用户本次点按的一部分，不能因为紧接着松开 C 就被清掉。

### 模块职责

- **hook.c** —— 底层键盘钩子线程。识别 C / 触发键 / D·F 修饰，维护 `volatile` 状态与"和弦门闩快照"（应对按键乱序到达），屏蔽映射期间的无效按键，并把动作需求投递给主线程。
- **main.c** —— 消息窗口 + 消息循环。和弦引擎（按住稳定期 → 首次开火 → 重复节奏）；路由：词跳动作用 `NavJump`，其余用 `SendActOnce` 发送；托盘菜单（暂停 / 退出）；日志 `CapLog`；启动时调用 `NavBaseInfo()` 采集环境基线（不落盘）。
- **nav.c** —— 词跳核心。多通道读取文本与光标（Edit / Scintilla / UIA / IA2）、字符分类算法、代理对处理、直接置光标、诊断 `NavProbe` / `NavBaseInfo`。
- **send.c** —— 模拟按键的唯一出口。扩展键标志（方向键/Home/End/Del 等必须带 `KEYEVENTF_EXTENDEDKEY`，否则扫描码被当成小键盘键）、逐条发送节奏、Ctrl/Shift 组合键的正确按住与释放。`SendInput` 的返回值会检查：目标窗口完整性级别更高时（UIPI）整批注入会被拒且返回 0，此前静默丢弃导致"词跳没反应而日志干净"，现在只在你按 **C + \`** 记录期间写一条日志。
- **act.c** —— 执行线程。串行执行会阻塞的发送动作（见上节），是"主线程不被发送过程占住"的保证。

### 和弦引擎要点（跨线程安全）

- hook 线程只改 `volatile` 标记 + `PostMessage`，主线程在单一消息循环里串行消费，避免竞态。
- **D/F 门闩快照**：按下动作瞬间的修饰由 `g_pendD/F`（物理顺序门闩）在开火时拷贝为 `g_actD/F`（开火快照），保证"动作先按、修饰后到"的乱序场景也正确。开火快照随 `ActJob` 一起投递给执行线程，**执行线程不读主线程状态**。
- **D 增益补齐**：短点（稳定期内抬起）动作补发到已发送 3 次；长按重复超过 3 次则不再补。次数由引擎在投递时给出，补齐函数不回写全局。
- **多键同按**：触发键的按下状态是**集合**（每个动作一个 bit）+ 引擎侧按下顺序栈。"最后按下"的动作生效，松开它之后退回上一个仍按着的键；每个键都能拿到属于自己的抬起事件。此前只记一个"当前按住的键"，J 按住时再按 K 会把 J 顶掉 —— J 的抬起再也发不出去，引擎就永远重复 J（表现为"一直输出左键"）。
- **空动作清理**：无待发 / 无激活动作且执行线程空闲时自动停表，避免残留状态。

### 卡键与键盘状态重置

修饰键"卡住"（OS 认为它还按着）的典型成因：组合键发到一半进程退出/重启，或目标程序吞掉了某个事件。判断卡键必须区分两种状态：

| 状态 | 含义 | 怎么拿到 |
| --- | --- | --- |
| **逻辑状态** | OS 认为该键是否按下（**被注入的键同样置位**） | `GetAsyncKeyState` / `GetKeyState` |
| **物理状态** | 用户是不是真的按着 | 只能由低级钩子自己记录（`PhysKeyDown`） |

**卡键 = 逻辑按下 && 物理未按**。仅看 `GetAsyncKeyState` 会得出相反结论（卡住的键恰恰是"被判为按下"的那些），这也是 AHK 要装键盘钩子才能支持 `GetKeyState(..., "P")` 物理状态的原因。

处理（与 AHK 同源的做法）：

- **托盘"重启程序" / 退出**：先按上述判据对修饰键补发抬起，再无条件补发**本进程注入过**的修饰键（这些键本不该残留按下状态）；用户真实按住的键不会被破坏。
- 释放 `Alt` / `Win` 前会插入一个中性掩码键（未定义虚拟键 `0xFF`），避免系统把孤立的 Alt/Win 抬起解释为"按下并释放 Alt/Win"而激活菜单栏或开始菜单 —— 即 AHK 的 `#MenuMaskKey` 机制。
- **`--reset-keys` 命令行**：不看任何状态，对所有修饰键各补一次抬起后退出，用于进程被强杀（状态表随进程消失）留下的卡键。可自建快捷方式：`CapsEnhance.exe --reset-keys`。

## 四、日志与诊断

- **日志文件**：`CapsEnhance.log`（与 exe 同目录）。**程序启动不生成日志**，仅当按下 **C + \`** 时开始写入，再按一次结束记录。结束记录时会把进程工作集压回（UIA/MSAA 的 COM 基础设施首次使用后常驻约 6~15MB，DLL 无法卸载；实测压测 400 次调用仅一次性增长 ~0.5MB 后平稳，非泄漏）。**注意隐私**：记录期间会写入焦点控件的文本样本（前 160 字符）与跳词位置，请在敏感内容上自行斟酌是否开启。日志是逐条开-写-关的，程序运行中随时可以用别的工具打开查看。
- **开始 / 结束提示音**：开始记录响"系统星号音"，结束记录响"系统手形音"，两音不同；同时托盘悬停提示变为"正在记录日志"。
- **焦点探测**：开始记录时自动探测一次当前焦点控件，结果**只写入日志**（并弹一次托盘气泡提示）。早先版本会弹模态对话框 —— 既冻住和弦引擎，2800 字符的正文在对话框里也读不完、复制不了。
- **启动环境基线**：启动时静默采集系统信息（进程位宽、钩子状态、OS 版本、管理员权限、键盘布局 / locale、UIA 自动化是否可用、屏幕与 DPI），保存在内存；开始记录时会随日志一并输出 `[启动基线]` 段，便于排查"某个窗口无法使用"时的环境问题。
- **托盘**：正常运行悬停提示"正在映射"；日志记录中提示"正在记录日志"；暂停时提示"已暂停"。菜单含 **重启程序**：对可能注入过的修饰键补"抬起"清掉卡键（物理按住的不动），随后拉起新实例（新实例带 `--wait-exit <旧PID>` 等旧进程完全退出后才装钩子）并退出本进程，钩子/和弦状态全部回到干净初态；退出时同样补一轮修饰键抬起。
- **内存**：主窗口禁用 IME/TSF（`ImmAssociateContext(NULL)` + 吞掉 `WM_IME_SETCONTEXT`，托盘菜单不再加载 textinputframework/CoreUIComponents 等）；"诊断结束"和"托盘菜单关闭"时把工作集压回待机内存（UIA 等 DLL 加载后无法卸载，只能压页；实测压测 400 次调用仅一次性增长 ~0.5MB 后平稳，非泄漏）。

## 六、注意事项

- 本程序拦截并屏蔽了 `CapsLock` 键本身；需要真实大小写切换时，用映射里的 `C + Tab` 发送 CapsLock，或从托盘"暂停"映射恢复原键。
- **单实例**：同时只允许一个实例运行。重复启动会直接退出，并让已在运行的实例显示"已在运行中"提示（重启流程内部通过 `--wait-exit` 握手，不受影响）。
- 现代编辑框（UIA/IA2 通道）无法像经典 Edit 那样一次设置光标，超长距离跳转会逐格发送方向键（上限 256 步）。
- **体量上限**：经典 Edit 通道（含 EmEditor）只处理 **64000 字符以内**的文档，超过就一步落到原生 `Ctrl+方向` 兜底 —— 实测经典 Edit 控件同样不提供 UIA/IA2 文本，四路一起失败，不会降级到 UIA 慢跳（逐档实测值与阈值见"二、词跳"里的通道表）。Scintilla 通道上限是 **2 MB**（文档字节数，中文 3 字节/字）。
- 托盘弹出菜单需要可聚焦窗口，CapsEnhance 启动时会创建 1×1 的隐藏顶层窗口用于承载系统菜单。
