## 架构总览

```
     底层输入钩子（键盘 + 鼠标）             主线程（消息窗口）
   ┌──────────────────────┐  PostMessage  ┌──────────────────────────┐
   │ hook.c               │ ────────────▶ │ main.c                   │
   │  LowLevelKeyboardProc│  WM_CAPS_*    │  窗口消息循环 + 和弦引擎   │
   │  LowLevelMouseProc   │  WM_TRIG_*    │  · 计时器 → 开火/重复     │
   │  · C / 触发键 / 修饰 │  WM_WHEEL_*   │  · ActPost() 投递动作    │
   │  · 模式门闩(keymap.c)│─────────────▶ │  · 滚轮注入/持续滚动投递  │
   │  · 屏蔽无效按键      │  WM_PROBE/TOGGLE│  · 托盘 / 暂停 / 日志   │
   └──────────────────────┘               └────────────┬─────────────┘
                                                      │ ActJob / ActWheelPostH / ActAutoScrollWheel
                                                      ▼
                                               ┌──────────────────┐
                                               │ act.c  执行线程   │
                                               │ 动作队列：会阻塞的 │
                                               │ 发送动作串行执行   │
                                               │ 滚轮注入/持续滚动  │
                                               │ 各自独立队列+线程  │
                                               └────────┬─────────┘
                                                        │ NavJump() / SendActOnce()
                                                        │ / SendWheelHNotches() / NavProbe()
                                                        │ / ActAutoScroll*()
                                                        ▼
                                               ┌──────────────────┐
                                               │ nav.c   send.c   │
                                               │  按词跳转：读取文本通道│ 模拟按键：扩展键
                                               │  + 边界算法       │ 标志/逐条节奏/
                                               │  + 诊断(NavProbe) │ Ctrl·Shift/滚轮
                                               └──────────────────┘
```

分层要点：

- **钩子**只做状态整理 + `PostMessage` 投递，**不阻塞**；一切"会阻塞的发送动作"都被投递到执行线程串行执行，主线程只维护和弦引擎状态。
- **滚轮**三路不走主线程注入：横向 / 快速滚动共用一条"滚轮通道"（独立队列 + 线程），持续滚动另有一条独立通道。它们的共同**硬要求**是：**绝不能跑在主线程上** —— 主线程一旦不在"等消息"状态，系统会把它那段到达的低级钩子事件直接跳过，松开 `Caps` 的 `keyup` 会丢失（`C` 修饰卡住 → 滚轮停不下来 + 之后按 `Tab` 冒出大写锁定）。

## 为什么会有 act.c（执行线程）

**`WH_KEYBOARD_LL` 的回调在"安装它的线程"上执行**（`dwThreadId = 0` 只表示"全局钩子"，不表示"系统线程"），钩子由主线程安装。一次按词跳转在主线程上可能连续阻塞数百毫秒：逐格方向键最多 256 步 × ~13ms、`SendNativeWordJump` 四个 40ms 组合间隔、`NavJump` 的跨进程同步 IPC（`SMTO_BLOCK`，单次最长 300ms）、UIA 的 COM 往返。**主线程被占住的这段时间，系统级键盘输入无法被钩子处理** —— 表现为全局输入卡顿；超过 `LowLevelHooksTimeout` 钩子还会被系统静默摘除，CapsEnhance "莫名其妙失效"却没有任何日志。

所以主线程只维护和弦引擎状态（按下即开火、重复节奏、动作栈），把"真正会阻塞的发送动作"整体投递到执行线程串行执行。投递项**自带开火快照**（D/F 修饰与已发送次数），执行线程**不回头读主线程的 volatile 状态**，两边只通过队列通信；队列是 FIFO，"先开火、后补齐"的顺序语义与原同步执行一致。

判断标准只有一条：**这段代码会不会让主线程阻塞超过 ~300ms？**（`LowLevelHooksTimeout` 的默认量级）。会，就必须搬走。

两个由此而来的约束：

- **`ActInFlight()` 门控**：同一时刻只让一发动作在飞。这正是原同步执行时的天然限速（主线程被占住时定时器根本跑不了）；少了它，长按按词跳转键会在队列里堆出一串尾流，松手后还在跳。
- **`ActClearKeepFill()`**：引擎复位时丢掉未开始的"重复开火"，但保留"松手补齐" —— 后者是用户本次点按的一部分，不能因为紧接着松开 C 就被清掉。

## 模块职责

| 文件 | 职责 |
| --- | --- |
| `keymap.c` | **键位映射的查询与装配**。动作表本身**不在这个文件里**，而在 `keymap_table.h` —— 它是"某个键是什么意思"的唯一一份定义，键位图（`help/help.c`）也要用同一份，两边各自 include，谁都不抄第二份。本文件提供查询接口（`ActOfVk` / `ActOutVk` / `ActWordDir` / `ActHasFlag` / `ActName`）与模式表（修饰模式 ↔ 激活键集合，激活键取自 `cap.h` 的 `MODE_*_KEYS_DEFAULT`，编译期常量、不读配置）。hook.c / main.c 只做查询。**引擎从不判断按的是哪个键，只问"这个模式生效了吗"**，所以"把 `D` 删掉只留 `Alt`"只改一处常量。启动时由 `KeyMapInit()` 装配 |
| `hook.c` | **底层输入钩子**。识别 C / 触发键 / 模式激活键，维护 `volatile` 状态与"事件时刻的修饰快照"，并**无条件跟踪真实 Shift**（横向滚动要用，且须放在"未按 C 就放行"之前）；屏蔽映射期间的无效按键；修饰键抬起使某模式失效时投 `WM_MODE_UP`。鼠标钩子只做一件事——按住 C 时把滚轮请求投递出去；**横向与持续滚动两路吞掉物理格**，只有放大档放行；回调在最热路径上，只允许几次比较 + `PostMessage` |
| `main.c` | **消息窗口 + 消息循环**。和弦引擎（按下即开火 → 重复节奏 → 松手补齐）；路由：按词跳转动作用 `NavJump`，其余用 `SendActOnce`；滚轮 / 持续滚动 / 模式失效消息只做投递；托盘菜单（暂停 / 设置 / 重启 / 退出）；`--restart` 等命令行开关；日志 `CapLog`；启动时调用 `NavBaseInfo()` 采集环境基线、`KeyMapInit()` 装配激活键 |
| `settings/settings.c` | **独立的设置程序**（`CapsEnhanceSettings.exe`，单独 exe，但链接 `src/config.c`）。**表单式**界面：布尔项 = 勾选框、数值项 = 数字框、五份名单各是一个可增删的列表（行内还有"选取窗口"：取到的值先填进输入框，点"添加"才入名单）；保存 = `ConfigSet*` + `ConfigSaveFile`（增量写回，保留注释/未知段/BOM/行尾） + `CapsEnhance.exe --restart`。为什么独立：本体主线程是钩子宿主，不能同时拥有设置窗口。为什么不做成文本编辑器：值域与布尔语义在 ini 里只是注释，摊开原文编辑等于允许写出"解析得出但不合理"的值。高 DPI：Per-Monitor V2 + `WM_DPICHANGED` 重排 |
| `nav.c` | **按词跳转核心**。多通道读取文本与光标（Edit / Scintilla / UIA / IA2 / WPS）、字符分类算法、代理对处理、直接置光标、诊断 `NavProbe` / `NavBaseInfo`。只把 WPS 当成"又一条通道"（一行分派），WPS 细节不在这个文件里 |
| `autodisp.c` | **通用**的 COM 自动化按名调用（`GetIDsOfNames` + `Invoke`：参数逆序、`PROPERTYPUT` 的命名参数、`EXCEPINFO` 里三个 BSTR 必须释放）。不认识任何具体程序；Word / WPS / Excel 这类对象模型都能用 |
| `bridge.c` | **通用**的"降权桥"：管理员进程访问"只有普通权限才看得见的对象"时的 IPC。只做运输，协议内容由调用方定义 |
| `wps.c` | **专用**的 WPS 文字通道：ProgID / 进程名 / 属性链 / 直接置位，以及跑在桥上的请求-应答协议。界面在 `src/auto.h` |
| `send.c` | **模拟按键与滚轮的唯一出口**。扩展键标志（方向键 / Home / End / Del 等必须带 `KEYEVENTF_EXTENDEDKEY`）、逐条发送节奏、Ctrl/Shift 组合键的正确按住与释放、滚轮加速的逐格补发、超限改道的判定（`SendArrows`）、`SendInput` 返回值检查（UIPI 拒绝时记录） |
| `act.c` | **执行线程**。串行执行会阻塞的发送动作；滚轮注入与持续滚动各有一条独立通道；持续滚动的状态机在锁内维护、由工作线程按拍输出 |
| `winmove.c` | **把焦点窗口挪到光标处**（`C+Q`）。落点计算是纯函数（单测覆盖多显示器几何）；执行部分只碰窗口几何：前台窗口 → `GA_ROOT` 顶层 → **全屏窗口直接拒**（`WinIsFullscreen`）→ **最大化且光标同屏则整个不动作**（结果不会变，做了只会闪）→ 还原（最小化/最大化）→ `MonitorFromPoint(DEFAULTTONEAREST)` + `MONITORINFO.rcWork` 钳制 → `SetWindowPos`。不认识键位（触发键在 `keymap.c`、分派在 `act.c`）。另：`WinIsFullscreen` 与 `WinIsShellClass` 是本模块对外提供的**共用判定**，`drag.c` 也用 |
| `drag.c` | **Caps+左键拖动窗口**。判定在鼠标钩子（按下那一刻决定吞不吞），执行在专用线程（"最新点 wins"，钩子每帧只写一次状态 + SetEvent）；含最大化异步还原、全屏（判据取自 `winmove.c` 的 `WinIsFullscreen`）/最小化/桌面/任务栏/黑名单的接管判定 |
| `ime.c` | **单键强制切换输入法**。判定在键盘钩子（"单击"），执行在专用线程（跨进程 IME 消息 + 键盘布局切换）；单槽 latest-wins，见[单键切换输入法](#单键切换输入法imec) |
| `folder.c` | **打开焦点程序所在文件夹**（`C+F3`），以及**打开日志文件所在位置**（日志结束气泡被点击时，走 `FolderRevealPath`）。走标准 shell 接口（`SHParseDisplayName` → `SHOpenFolderAndSelectItems`，**不拼 `explorer.exe` 命令行**）；目标窗口由 `ActJob.hwnd` 在开火那一刻快照；执行在自己的**一次性线程**上（MTA + `CoInitializeEx`），不占 `act.c` 的动作队列；UWP 走"宿主 `ApplicationFrameHost` → 子窗口 `Windows.UI.Core.CoreWindow` → 真实进程"；失败原因经 `WM_FOLDER_OPEN` 回主线程弹气泡。两个入口共用同一个 `FolderJob` 与线程过程 |
| `help.c` | **按键帮助的开合（主程序侧）**（`C+F1`）：拉起同目录的 `CapsEnhanceHelp.exe`，并把"当前该显示还是该隐藏"告诉它（注册消息 + 40ms 对账重试）。窗口**不常驻**，所以每次显示都是一次冷启动 —— 而"按一下就松手"会让 SHOW/HIDE 都发在窗口出生之前，重试就是为这个竞态准备的。寿命由和弦决定：按下开、抬起关、松开 Caps（`ResetEngine`）也关 |
| `help/help.c` | **按键帮助窗口本体**（独立 exe `CapsEnhanceHelp.exe`）。自包含：不装钩子、不初始化 COM/TSF，只做"GDI+ 起一次 + 铺底一帧 + GDI 画一遍字 + 送进分层窗口"（只读 `CapsEnhance.ini` 里那三个 `Ime*Mode`，用来决定底部三条"单击切输入法"的文案）。逐像素 alpha（32bpp DIB + `UpdateLayeredWindow`）实现半透明；文字用 **GDI + ClearType**；`WS_EX_NOACTIVATE` 保证不抢焦点；键位表从 `keymap_table.h` 编进来（不跨进程取数据）。见[按键帮助](#按键帮助helphelpc) |

> 分层意义：以后要支持"另一个只有 COM 才读得到的程序"（如 WPS 表格），照 `wps.c` 再写一个文件即可，`autodisp.c` 与 `bridge.c` 原样复用。
> 激活键（`Alt/D`、`F`）**不做成配置项**：它们属于和弦语法本身，改变量级 < 配置项，历史实装成 `EnhanceKeys` / `ShiftKeys` 后已回退（改它们等于改功能）。但 `keymap.c` 那层模式抽象仍在，以后想改常量只需动 `cap.h` 一处。

## 跨线程安全与和弦引擎要点

- **`volatile` 与 `std::atomic` 的分界**（容易搞混，先看这条）：`volatile` **不是同步原语** —— 它只阻止编译器优化，不建立 happens-before、也不保证原子性。所以"跨线程用的标志"必须用 `std::atomic`。本项目里**真正跨线程**的用户态标志有三组：`g_recording`（主线程写，`act.c` / `send.c` / `nav.c` 的**工作线程**读它决定要不要写日志）→ `std::atomic<bool>`，读写显式写 `.load()` / `.store()`；`send.c` 的 `g_injectedDown`（工作线程写、主线程退出时读）→ 同样 `std::atomic<bool>`；以及 `send.c` 的逐格打断标志 `g_arrBusy` / `g_arrDir` / `g_arrBreak`（前两个 act **工作线程**写、主线程钩子读，`g_arrBreak` 反过来）→ 它们是"意图"标志、最坏只晚一拍响应，仍用 `volatile`。
  其余声明为 `volatile` 的标志（`g_cMod` / `g_shiftMod` / `g_state.paused` / `g_actEnh` / `g_actShf` / `g_btnCount`）**都不跨线程**：两个低级钩子都由主线程 `SetWindowsHookEx` 安装，于是键盘回调、鼠标回调与窗口消息处理**全在主线程上串行**；工作线程刻意不读它们（开火快照随 `ActJob` 传值过去）。那些 `volatile` 的真实作用是防"编译器把循环里的读取提升到循环外"（回调是**异步进入**的，编译器看不出来），**不是**同步。
- hook 回调只改上述标记 + `PostMessage`，主线程在单一消息循环里串行消费，避免竞态。
- **开火快照（修饰）**：`main.c` 在**按下触发键那一刻**把快照读进 `g_actEnh` / `g_actShf`，随 `ActJob` 一起投递给执行线程。快照来源是钩子随 `WM_TRIG_DOWN` 带来的 `TRIGF_*` 位（事件时刻的状态），不是消息处理时现读 `ModeDown()`——钩子回调与消息处理异步，现读会读到"修饰已经松开"（见下方"修饰快照取事件时刻"）。早期那份 `pendMask` 门闩（`ModePending`）与 `downMask` 同步置位/清除、恒等，从未真正生效，已在代码审查 P1-1 中删除；现在以 `ModeDown()` 为唯一判据。
- **顺序语义：修饰键必须先按住，再按触发键**。按下即开火，不等任何"稳定期"。反向顺序（先按 J、再按 Alt/D）就是一次不带增强/选区的普通动作，不补正。这里曾有一个 `CHORD_SETTLE(50ms)` 稳定期（按下后等修饰到位再开火），用来兜住"J 先按、D 后到 ≤50ms"的乱序组合；代价是**每个**触发键都白等 50ms 才响应（实测按下→开火 57~71ms），已删除。
- **增强模式补齐**：点按（按下即抬起）动作补发到已发送 3 次；长按重复超过 3 次则不再补。次数由引擎在投递时给出。**开关键（`C+Tab`）不参与重复与补齐**（`ACTF_SINGLE_SHOT`）。一次点按现在是两条请求：按下开火（`fillAct` 为空）+ 抬起补齐，两条都带 `keep` 标志（见 `ActJob`）——`ActClearKeepFill` 只保留 `keep` 为真的请求，若按"`fillAct` 非空"判据会把开火那条当尾流丢掉。
- **多键同按**：触发键的按下状态是**集合**（每个动作一个 bit）+ 引擎侧按下顺序栈。"最后按下"的动作生效，松开后退回上一个仍按着的键。此前只记"当前按住的键"，J 按住时再按 K 会把 J 顶掉、J 的抬起发不出去 → 永远重复 J。
- **空动作清理**：无待发 / 无激活动作且执行线程空闲时自动停表，避免残留状态。

### 修饰快照取"事件时刻"，不是"消息处理时刻"

钩子回调与主线程的消息处理是**异步**的。用户"点按 J 之后立刻松开 Alt"时，Alt 的抬起**已在钩子里**清掉按住位图（同步执行），而 `WM_TRIG_UP` 还排在队列里——主线程那时再读"修饰键按住了吗"会读到"已经松开"，点按补齐于是**时有时无**。

所以钩子在**事件发生的那一刻**取修饰快照，随消息带给主线程（`WM_TRIG_DOWN` / `WM_TRIG_UP` 的 `lParam`，见 `cap.h` 的 `TRIGF_*`）。**按下**那条的快照决定本次动作带不带增强/选区；**抬起**那条的快照只进诊断日志（引擎在按下时就把动作开了、快照随 `ActJob` 冻结，抬起只做"停重复 + 按增强模式补齐"）。长按重复路径不重新采集：一次按下的修饰快照贯穿这次按住期间的所有重复。

## 卡键与键盘状态重置

修饰键"卡住"（OS 认为它还按着）的典型成因：组合键发到一半进程退出 / 重启，或目标程序吞掉了某个事件。判断卡键必须区分两种状态：

| 状态 | 含义 | 怎么拿到 |
| --- | --- | --- |
| **逻辑状态** | OS 认为该键是否按下（**被注入的键同样置位**） | `GetAsyncKeyState` / `GetKeyState` |
| **物理状态** | 用户是不是真的按着 | 只能由低级钩子自己记录（`PhysKeyDown`） |

**卡键 = 逻辑按下 && 物理未按**。仅看 `GetAsyncKeyState` 会得出相反结论（卡住的键恰恰是"被判为按下"的那些）——这就是 AHK 需要键盘钩子才能支持 `GetKeyState(..., "P")` 物理状态的原因。

处理（与 AHK 同源的做法）：

- **启动时先清一次卡键**：按"系统认为按着 **且** 用户物理上没按"补一次抬起。判据天然排除此刻真按着的键。
- **托盘"重启程序" / 退出**：先对修饰键补发抬起，再**无条件补发本进程注入过**的修饰键；用户真实按住的键不会被破坏。
- 释放 `Alt` / `Win` 前插一个中性掩码键（未定义虚拟键 `0xFF`），避免系统把孤立的 Alt/Win 抬起解释为"按下并释放"而激活菜单栏 / 开始菜单 —— 即 AHK 的 `#MenuMaskKey` 机制。

## 托盘图标"开机后时有时无"（UIPI + 启动时序）

现象：计划任务的**管理员自启**（`/rl HIGHEST`）偶尔不给图标，手动重启程序就好。两个成因叠在一起，缺一个都解释不了"不稳定复现"：

| 成因 | 机制 | 对策 |
| --- | --- | --- |
| **起得太早** | 自启发生在用户登录瞬间，explorer 的通知区常常还没建好 → `Shell_NotifyIcon(NIM_ADD)` 直接失败 | **看返回值**，失败就 `SetTimer` 定时重试（1.5s × 最多 120 次），成功后再重建完整悬停提示 |
| **收不到"补图标"的通知** | 任务栏建好后，系统只靠一条广播 `TaskbarCreated` 通知。本进程是**高完整性**（管理员），explorer 是**中完整性** —— 低 → 高 的广播被 **UIPI 默认丢弃**：那条消息根本没到我们的窗口过程 | 建窗后对 `s_taskbarCreated` 调 `ChangeWindowMessageFilterEx(..., MSGFLT_ALLOW)`（与 `WM_RESTART_REQUEST` 同一条规矩） |

两条都要有：白名单只覆盖"explorer 后来重启"，重试覆盖"我们起得太早"（那种情况下广播**早于**本进程存在，本来也收不到）。

细节：
- 重试用 `SetTimer` / `WM_TIMER`，**不是** `Sleep` 轮询 —— 主线程一旦离开"等消息"状态，低级钩子会被系统静默摘除。
- 图标句柄为 `NULL` 时 `NIM_ADD` **照样返回 TRUE**，但通知区里是一块空白（看不见也点不到）—— 属于重试查不出来的那种失败，所以加了一道退回系统图标的兜底并记日志。
- 诊断看日志：首次失败会写 `托盘：首次添加图标失败（任务栏尚未就绪）`，恢复时写 `托盘：图标在第 N 次重试后添加成功`；`N` 就是"任务栏晚到了多久"。

## 命令行接口与"让在跑的实例重启"

| 开关 | 行为 |
| --- | --- |
| `--restart` | 找到运行中的实例 → 向它投 `WM_RESTART_REQUEST` → 自己立即退出。**没找到实例就照常启动**（不退出） |
| `--wait-exit <pid>` | 重启握手：等旧实例退出（最多 5s）后再初始化，避免两个实例的钩子/托盘并存 |
| `--bridge <pid> <seq>` | 降权桥的子进程模式（见 `bridge.c`） |

`--restart` 是给**外部程序**用的唯一入口（设置程序保存配置后走的就是它）。它不带任何进程内知识 —— 靠 `FindWindowW(L"CapsEnhanceMain")` 找窗口、`PostMessage` 投一条约定消息，因此跨进程、跨语言都能用。

设置程序的写回走 `ConfigSaveFile`（config.c）：**增量**更新 ini —— 已有键就地替换值、缺失键补到 `[General]` 末尾（连同 `kUpgrades` 那份注释块，值是当前值不是默认值）、名单段保留注释重建名字行、未知段/未知键原样保留、BOM 与 LF/CRLF 跟随原文件。整份重写会把用户写的注释一起冲掉，那是"我写的东西没了"级别的问题。

两个容易踩的点：

- **UIPI**：Windows 默认拦掉"完整性级别低 → 高"的 `PostMessage`。而开启 `RunAsAdmin=1`（**默认 0**）意味着本体常驻实例**是**管理员，而设置程序往往是普通权限 —— 不放行的话"保存并重启"会**静默失效**（消息被丢弃、没有任何报错）。所以窗口建好后对 `WM_RESTART_REQUEST` / `WM_ALREADY_RUNNING` 调 `ChangeWindowMessageFilterEx(..., MSGFLT_ALLOW, ...)`。
- **顺序**：`--restart` 的处理必须排在**单实例检查之前**，否则"已经有一个在跑"会让它连消息都发不出去就退出了。

## 自动屏蔽（`[AutoDisable]`）

名单里的程序在前台时，**本程序整段不介入** Caps 开头的和弦：CapsLock 恢复正常功能，`C+任意键` 照常打字，`Caps+滚轮` 也不放大。

- 判据在**按下 Caps 那一刻**查一次（`ConfigIsAutoDisabled(GetForegroundWindow())`），命中就走"反着按"那条已经在用的不介入路径（`g_capsSkip`）—— 吞/放天然对称，不会造出"down 放行、up 被吞"的卡键。
- **不做成运行时的 `g_state.paused`**：暂停是**用户显式**切的，自动屏蔽是**按前台程序**随时变的；同一份状态就分不清"用户自己暂停的"和"程序自动让开的"，托盘也不知道该显示哪个。
- 名单为空时 `MatchFocus()` 直接短路，一次 `OpenProcess` 都不做 —— 大多数人不用这功能，不该为它付代价。
- 状态**变化**时才 `PostMessage(WM_AUTODISABLE)` 改托盘提示（悬停提示要走一次 `Shell_NotifyIcon`，没必要每次按 Caps 都做）。

## 按词跳转（WordJump）实现

`N` / `O` 不做简单的 "Ctrl+方向"，而是**读取控件真实文本**，按自定义边界算法跳到目标位置，因此在中文、英文、数字、生僻字混排文本里更稳定。

### 字符分类（反向判定）

每个字符归为一类，**连续同类字符串视为"一个词"**：

| 类别 | 说明 |
| --- | --- |
| `CH_OTHER` | 剩下的"其他"字符：汉字、其他语言文字、生僻字、emoji 等 |
| `CH_ALPHA` | 字母 + 数字（含全角）——同一组，`21M` 是一个词 |
| `CH_HANGUL` | 谚文（韩文）自成一组 |
| `CH_SEP` | 分隔符：空白 + 标点（ASCII / 全角 / CJK 标点） |

采用**反向判定**：先枚举字母数字 / 符号归入对应类，剩下的全部归 `CH_OTHER`——因此汉字等无需逐个枚举码位，天然连成一类。

### 跳转语义

- 左右跳都在"词的边界"（类型切换处）停。
- **默认不跨行**：分隔符串只在行内跨（空格 / 制表），`\r` / `\n` 不跨——行首右跳停在本行行尾，行中左跳停在本行词首。
- **只有出发点已在行尾 / 行首才跨行**：行尾右跳 → 下一行行首词（跳过缩进）；行首左跳 → 上一行行尾词（跳过行尾空格）；相邻空行会被跳过。
- **代理对（补充平面字符，如扩展 G 区生僻字）当作一个字符整体**，不会拆散；光标落在代理对中间这类异常位置会被归一。

### 文本读取通道（按优先级尝试）

读不到文本、或读回的文本被判定为占位时，自动沿下一个通道继续；**全部失败**才发原生 `Ctrl(+Shift)+方向键`。各通道有各自的体量上限：

| 通道 | 体量上限 | 超过上限时 |
| --- | --- | --- |
| 经典 Edit / RichEdit / EmEditorView | 64000 字符 | 放弃本通道：`EM_GETSEL` 把选区起止打包进返回值的 `LOWORD` / `HIWORD`，每端只有 16 位，更长的文档读回的光标会回绕成错位值 |
| Scintilla 系 | 2 MB（文档字节数） | 放弃：不为巨型文件开跨进程读缓冲 |
| UIA / IA2 | 读回文本 < 2 字符 | 视为占位假文本，放弃 |
| WPS 文字（COM） | 100000 字符 | 放弃：整篇文本要经 COM / 管道搬一遍 |
| 原生 Ctrl+方向 | —— | 兜底，不再往下 |

> 实测：真实 `Edit` 控件下，64000 字符都走经典 Edit 通道；64001 字符起 Edit / Scintilla / UIA / IA2 四路全部失败，直接落到原生 `Ctrl+方向`。经典 Edit 控件既没有 UIA 也没有 IA2 文本，超限就是一步退到底，不会"降级到 UIA 慢跳"。

各通道要点：

1. **经典 Edit / RichEdit / EmEditorView**：`WM_GETTEXT` + `EM_GETSEL`。白名单外不放行（Chromium 系窗口对这两条消息回的是标题和垃圾值）；直接置位后回读校验，控件只实现半套协议时自动退回逐格箭头。两条防线：`EM_GETSEL` 的值超出文本长度 ⇒ 单位不一致（该控件按字节计位置）⇒ **整条通道放弃**；**连续两次直接置位无效**（返回成功但光标没动，WPF 一类实现如此）→ 本次会话内对该进程不再尝试置位（`g_noSetProc` / `g_noSetCount`，重启恢复，避免光标反复空闪）。
2. **Scintilla 系**（Notepad3 / Notepad++ / SciTE）：`SCI_*` 窗口消息。文档以字节为单位（UTF-8 下中文 3 字节/字），整条通道在字节域取原始文本再转 UTF-16 交给词边界算法；`SCI_GETTEXT` 的缓冲区指针属于对方进程，必须先 `VirtualAllocEx` 再读回。跳距 ≥ 6 用 `SCI_SETSEL` 瞬跳。
3. **UIA** `TextPattern`/`TextPattern2`：支持 QQ、Edge 等 Chromium/WinUI 控件。锚定顺序：焦点元素沿祖先链 → 焦点 HWND 沿祖先链 → 焦点 HWND 子树检索；读回文本短于 2 字符视为占位弃用。
   - **Electron 编辑器**：无障碍节点（`role=textbox` 的 div）只有在开启无障碍模式（或系统检测到读屏器）时才写入光标附近的真实文本并同步选区——否则外部读到的是 1 字符占位。**开启后按词跳转引擎（含中文混排、不跨行）可完整工作**，未开启则走原生 `Ctrl+方向` 兜底（或加入 `[NativeWordJump]`）。平滑光标等纯视觉动画无关。
4. **IAccessible2** (`IAccessibleText`)：其余无障碍文本控件（同样弃用短于 2 字符的占位读回）。UIA / IA2 跳完会**回读校验**：仍是同一页文本且坐标可比时按差值补发一轮；偏差超过原步数说明该程序文本坐标与实际光标系统性不符（短跳准、长跳超调），**本次放弃补正，不做自动切换**——这类请加入配置名单。
5. **WPS 文字**：走 COM 自动化（见下节）。
6. 全失败则原生 `Ctrl(+Shift)+方向键` 兜底——**Ctrl 必须真的按住**（在方向键之前按下、之后抬起），否则目标收到的只是单格方向键。

> **跨进程消息坑**：`SendMessageTimeout` 的返回值只表示"是否发送成功"，窗口过程的返回值必须通过 `lpdwResult` 取。传 `NULL` 拿到的是恒为 1 的状态值——曾导致 `WM_GETTEXTLENGTH` 恒等于 1，文本永远只读到一个字符、词边界算法整个失效。

> **UIA 引用计数坑（表现为闪退）**：沿祖先链找 `DocumentRange` 的函数顺手把调用方传进来的元素也 `Release` 了——它只拥有 `GetParentElement` 拿到的那些引用，传进来的是**借来的**。WPS 不提供 UIA 文本，每次按词跳转都走失败路径，于是每次对调用方元素多释放一次、引用计数归零、对象被销毁，调用方的 `Release` 读到已释放内存里的 vtable → `c0000005`。**COM 里"借来的接口指针绝不能 Release"**——只有 `AddRef` 过或规则上归你的才释放。

### 直接置光标（远跳提速）

跳转距离 ≥ 6 个字符时**直接置位**（瞬跳），小距离仍发真实方向键；置位后回读校验，控件不配合就退回逐格箭头。

| 通道 | API | 备注 |
| --- | --- | --- |
| 经典 Edit | `EM_SETSEL(锚, 活动端)` | **活动端在 lParam**（emprobe H 段实测：置位 `(60,73)` 后 `Shift+Left` 动的是 73、置位 `(73,60)` 后动的是 60）。区间会被有序化，所以**只有传参顺序能决定光标落在哪一端** —— 传有序区间会让向左扩选后的光标停在右端 |
| Scintilla | `SCI_SETSEL(anchor, caret)` | 活动端 = `caret`（第二个参数），置位后用 `SCI_GETCURRENTPOS` 回读校验，本来就是对的 |
| UIA | `TextRange.Select()` | 退化（空）range 上调用 Select 即移动光标。**仅限无 Shift**；Chromium 系对折叠 range 的负向端点移动一律拒绝，向左目标用正向增量 + 绝对定位构造 |
| IA2 | `setCaretOffset` / `setSelection` | 不支持时返回 `E_FAIL` 退回箭头；**仅限无 Shift** |
| WPS | `Selection.SetRange(活动端, 锚)` | **活动端在第一个参数**（与 Edit 相反）—— 实测 `[12,31]` 后 `Shift+右` 得到 `[13,31]`，动的是起点。`start == end` 即移光标；**带 Shift 或已有选区时必须走它** |

- **"活动端落在哪个参数上"各通道不同，不能统一传有序区间**（2026-09-12 修）：Edit 在 `lParam`、WPS 在首个参数、Scintilla 在 `caret`。统一传 `(小,大)` 的后果是"向左扩选后光标停在右端、向右扩选后停在左端"，紧接着按方向键时"取消选中"的方向与直觉相反。区间本身两种顺序等价，**只有传参顺序影响活动端**。
- UIA / IA2 的位移**仅限无 Shift**：带选区时读回的位置是选区起点而非活动端，目标计算不成立——Shift 位移走箭头（anchor 语义天然正确）。WPS 置位**不限无 Shift**（`SetRange` 吃有序区间，位移序列锚点由自己维护）。
- **置位并非对所有 UIA 实现有效**：Chromium 系支持（只支持移动 End 端点）；**WPF 系（如 Quicker 文本框）的 `Select()` 会返回成功但选区不动**，还会让显示光标短暂闪到目标却不真正生效——连续两次判定无效后本会话内对该程序不再尝试置位（消除闪烁，重启程序恢复），回读发现"光标未动"后自动退回箭头。
- UIA / IA2 置位回读比经典 Edit 更严：仍同一页文本且光标恰在目标才算成功；HRESULT 成功但回读不符时不叠加箭头（避免双重错误）。
- 三个通道置位后都让视口跟随：Edit `EM_SCROLLCARET`、Scintilla `SCI_SCROLLCARET`、UIA `ScrollIntoView`。

三个实测坑（都用 `test\emprobe.c` 一次性探测工具钉住）：

1. **`WM_GETTEXT` 返回计数把结尾 NUL 算进去** → 已剥掉。
2. **位置单位随文档编码变**：UTF-16 文档给字符下标，**UTF-8 文档给字节偏移**（73 字符的文档回 181）。判据：`EM_GETSEL` 的值超出文本长度 ⇒ 单位不一致 ⇒ **整条通道放弃**。曾经把越界值钳到文本末尾，把"模型假设被打破"这个信号抹掉了，最后拿错位的字节值去置位、把光标写到多字节字符中间。
3. **外部 `EM_SETSEL` 置位后，它会吞掉紧接着的第一次输入**（现象："跳词后按 J 要按两下才动"）。实测**与时间无关**（隔 1.2s 按的那次照样被吞）——是"次数"不是"时间窗口"，所以可以主动喂掉：置位后发**一支探针方向键**，再回读校准（光标没动=确实被吞，探针无痕；动了=这次没被吞或被用户抢先按掉，反向补一格回来）。带 Shift 时**不发探针**（无 Shift 的方向键会折叠刚设好的选区）。探针必须走 `SendInput`（`PostMessage` 的 `WM_KEYDOWN` 它不认）。
   > 早先这里写的是"跳完按差值自校验补发"，但补正代码的条件是 `!direct` —— 恰好把"置位之后"这条路径排除在外，那个坑只被记录、从未被真正解决。

同一次探测还确认了两条**走不通**的路：EmEditor 没有注册 COM 自动化（`CLSIDFromProgID("EmEditor.Application")` = `0x800401F3`）；它也不支持 `EM_POSFROMINDEX` / `EM_LINEFROMCHAR` / `EM_LINEINDEX` / `EM_GETRECT`（恒返回 0）。所以"算出目标坐标再后台点击"这条思路在它身上不成立——点击本身它是有反应的（`PostMessage` 的 `WM_LBUTTONDOWN/UP` 能让光标动），但**没有"字符 → 坐标"的来源就没法知道该点哪儿**。

第三个坑（`OverStepMode=1` 的改道）：**改道之后必须回读落点**。改道只是把这一跳交给目标程序自己的词导航，而**它的词切分跟我们的算法不一定一致**——实测 QQ（Chromium）的 `Ctrl+←` 按 ICU 词典切、一次只走 1 个字，而我们按"连续汉字段"整段算（一次十几字），结果光标落在整段中间、左右还不对称。所以改道后一律回读光标：与目标不符就按差额逐格补足（`SendArrowsStrict`，**不再判一次超限**，否则补正自己又被改道）；`OverStepMode=0` 的"只发一格"是既定行为，不补。

## WPS 文字：COM 自动化 + 降权桥

WPS 文字**完整实现了 Word 的对象模型**（窗口 / 控件类名都照抄 Word：`OpusApp` / `_WwG`；`Application.Name` 自报 `"Microsoft Word"`），所以可以当一个"Word 自动化客户端"读它文档引擎里的真数据：

| 要的东西 | 取法 | 说明 |
| --- | --- | --- |
| 全文 | `Application.ActiveDocument.Range().Text` | **不能用 `Document.Content`**——WPS 上 `Content.Start/End` 取不到（实测 -1） |
| 光标 | `Application.Selection.Start` | 段落分隔符是 `\r`，与 `Range.Text` 下标一致 |
| **直接置位** | `Selection.SetRange(start, end)` | 一步移光标（`start == end`）或建选区，免逐格发方向键 |

**直接置位实测**（`test\wspset.c` 可复现）：

| 调用 | 结果 | 结论 |
| --- | --- | --- |
| `Selection.SetRange(10, 20)` | 成功，且参数**自动有序化** | **采用**：绝对定位、语义清晰 |
| `Document.Range(2,8).Select()` | 成功（选区恰好等于该区间） | 可用（`SetRange` 少一次对象获取，故未选它） |
| `Selection.Start = 5` | 成功但**不折叠选区**：`[12,12]` 变 `[5,12]` | **不能用**："移光标"必须发 `SetRange(t, t)` |

**★ WPS 的"活动端"和我们的模型不一致**（踩过的坑）：`SetRange(a,b)` 之后 WPS 认为活动端是 **a**，于是它那里的 `Shift+方向` 会去动另一端——实测选区 `[12,31]` 按一次 Shift+右 得到 `[13,31]`（动了起点）。带选区时普通方向键往哪一端折叠也由它决定。所以只要有 Shift **或**当前已有选区（`caret != selEnd`），就必须走绝对置位，绝不混用箭头；只有"小距离且光标折叠"才发箭头。

附着方式用 **ROT（运行对象表）+ `GetActiveObject(CLSIDFromProgID("KWPS.Application"))`**，因为 `CoCreateInstance` 会**另起一个没有文档的 WPS 进程**，读不到用户窗口里那篇文档。

> WPS 的 ProgID：文字 `KWPS.Application`、表格 `KET.Application`、演示 `KWPP.Application`。本项目**只支持文字**。判定"是不是 WPS"必须**按进程名**（`wps.exe`）而不是窗口类名——类名跟真正的 Word 一模一样，按类名判会把 Word 也卷进来。

**★ 关键限制：COM 的 ROT 按完整性级别（UIPI）隔离。**

| 运行权限 | `GetActiveObject` | 结论 |
| --- | --- | --- |
| 普通用户（Medium） | 成功（实测） | 本进程直接读 |
| 管理员（High） | **恒失败 `0x800401E3` (MK_E_UNAVAILABLE)** | 即使 WPS 文档开着、窗口失去过焦点、甚至借普通令牌 `ImpersonateLoggedOnUser` 模拟，依然失败 |

所以**管理员运行时**改由一个**普通权限的子进程**代读（"降权桥" `src/bridge.c`）：

- 父进程用 `explorer.exe` 的令牌 `CreateProcessWithTokenW(..., LOGON_WITH_PROFILE, ...)` 拉起 `CapsEnhance.exe --bridge <pid> <seq>`（同一份 exe 的普通权限副本：不装钩子、不建窗口 / 托盘、不参与单实例）。
- ⚠ **`CreateProcessAsUser` 用不了**：它需要默认**未启用**的 `SeAssignPrimaryTokenPrivilege`（实测报 1314），而管理员令牌里该特权是"未分配"，不是"未启用"。
- ⚠ **不能用句柄继承传管道**：`CreateProcessWithTokenW` **不支持句柄继承**（没有 `bInheritHandles` 参数）。
- **命名管道由子进程创建**（对象带普通权限的完整性标签），管理员父进程再去连——高完整性写低完整性对象允许，反向才被拦。管道名带父进程 pid 与递增序号；空闲 120s 自退、管道断开即退、父进程退出时显式发停止帧；子进程另有"父进程监视线程"，父进程一没就收工（否则父进程死在"已拉起、还没连上"的窗口里会留下孤儿）。
- **这条桥是通用的**（`src/bridge.c`）：只提供"降权拉起 + 长度前缀帧收发 + 生命周期"，不认识 WPS。目前只有 `'G'`（取文本）/ `'S'`（置选区）两条命令；将来再有"只有普通权限才看得见的对象"，照 `wps.c` 再写一个文件即可。
- 首次在 WPS 里按键时**按需拉起**（`LOGON_WITH_PROFILE` 要加载用户配置，偶发要几百毫秒，等待窗口给到 1.5s）；桥起来后常驻复用。桥失败退避 1s 再试，期间该次按词跳转按"读不到文本"退回原生 `Ctrl+方向`。
- 子进程诊断写进同一个日志，行首带 `[桥WPS]` / `[桥]` 前缀。

WPS 置位的回读校验返回**三态**：

| 返回 | 含义 | 调用方怎么做 |
| --- | --- | --- |
| `WPS_SET_OK` | 已生效且回读一致 | 本次结束，不再发箭头 |
| `WPS_SET_NONE` | 光标完全没动 | 可安全退回逐格箭头 |
| `WPS_SET_UNSURE` | 读不回来 / 动到了别处 | **绝不再补箭头**（两个错误叠加更糟） |

命令行自查：跑 `test/wpsjump.exe`（真机集成测试：直调 `NavJump`，从外面独立回读 `Selection`
核对落点；没装/没开 WPS 时打印 `[SKIP]` 并以 0 退出）。

另外：焦点控件的取法要兜住"取不到"——`GetGUIThreadInfo` 只报告属于该线程输入队列的焦点窗口，而 WPS 的文档控件在**另一个线程**上，前台是 `OpusApp` 时 `hwndFocus` 为 `NULL`。取不到时退回**前台窗口本身**（各通道自带类型判定，WPS 通道判进程名，有前台窗口就够）。

## 窗口挪到光标处（`winmove.c`）

一句话：`GetForegroundWindow()` → `GetAncestor(GA_ROOT)` → 还原（最小化/最大化）→ `MonitorFromPoint(…, MONITOR_DEFAULTTONEAREST)` + `MONITORINFO.rcWork` → `SetWindowPos`。

几个决定与其理由：

- **落点 = 窗口左上角对齐光标，再整窗钳进 `rcWork`**。取 `rcWork` 而不是显示器全矩形：`rcWork` 已排除任务栏与桌面工具栏，钳进它才能保证"整窗可见、不压托盘"。窗口比工作区还大时按左上角对齐（钳不出更优解，但至少标题栏在）。
  **为什么不用"中心对齐"**：居中必须按尺寸换算落点（`左上角 = 光标 − 尺寸/2`），而尺寸是**对方的** —— 它跨屏时可能自己改尺寸（实测 CLaunch 在 125% 屏上 578x437、到 150% 屏上变 495x374），按旧尺寸算出的中心立刻就偏了（实测偏 41px），表现出来就是"按一下没完全过去、再按一下才对"。左上角对齐**不依赖尺寸**：它怎么改都不影响落点。尺寸仍然要读，但**只为钳制**（保证整窗可见），不再参与落点计算。
- **`MONITOR_DEFAULTTONEAREST` 不是可选项**：官方文档写明它返回"离该点**最近**的显示器"，于是"光标落在两屏之间的缝里""改过分辨率/拔过屏、坐标悬空"都能兜住，而不是整条路径失败。
- **最小化/最大化窗口必须先 `SW_RESTORE`**：最大化的窗口位置由系统按所在显示器算、传给它的 `(x,y)` 会被忽略；最小化的窗口 `GetWindowRect` 拿到的**不是**还原位置（照着算就会挪到错的地方）。最大化那条最后再 `SW_MAXIMIZE` 回去，等价于 `Win+Shift+方向` 的语义（状态不变、只换屏）。
- **最大化 + 光标同屏 = 连还原都不做**：整套"还原 → 挪 → 最大化"落点一模一样，用户只看到小窗口闪一帧 —— 正是「最大化窗口按 `C+Q` 会抖动」的现场。判据是**两块显示器**（`MonitorFromPoint(光标)` vs `MonitorFromWindow(窗口)`）相同，只在 `wasMax && !wasMin` 时做；命中就返回 `TRUE`（动作处理完了，别让 act.c 记"没有可挪的前台窗口"）。这与 `drag.c` 的拖出阈值是同一个设计判断：**结果不会变的变化就不要发生**。
- **"请求 → 回读锚点 → 重试"最多 3 次**（`MOVE_TRIES`）：回读只比**左上角**（右/下两边不判 —— 对方改尺寸是它的自由，左上角对了窗口就是"从这里开始"）。这一步针对的是**收到移动请求后又自己挪走**的程序（带吸附/跟随行为的启动器、面板类工具）；"自己改尺寸"那一类已经被左上角对齐免疫了。判据必须挑"能被破坏的量"：**不能**用"光标在不在窗口里" —— 窗口自己缩小之后光标仍在窗口内，那个断言恒真、测不出区别（写测试时真踩到了）。
- **一律带 `SWP_ASYNCWINDOWPOS`**（对方线程卡住不拖住执行线程；文档：调用线程与窗口所属线程不在同一输入队列时系统把请求**投递**过去）。代价是**回读会抢在请求生效之前** → 回读前先 `Sleep(MOVE_SETTLE_MS)` 让一小会儿。顺带解决了"最大化必须等位置生效"：确认锚点就位之后才 `SW_MAXIMIZE`，否则最大化可能先执行、把窗口铺回**原来**那块屏。
- **只挪顶层窗口**：Chromium 系 / UWP 的前台窗口往往是内容子窗口，挪它等于把它从父窗口里撕出来 → 一律 `GetAncestor(GA_ROOT)`。桌面（`Progman` / `WorkerW`）与任务栏（`Shell_TrayWnd` / `Shell_SecondaryTrayWnd`）按类名挡掉；前台是本进程自己（托盘菜单）时也直接返回。
- **全屏窗口不动**，而且判定必须在 `SW_RESTORE` **之前**。全屏窗口在系统眼里就是"最大化铺满"，照原流程走是 `SW_RESTORE` → `SetWindowPos` → `SW_MAXIMIZE` 又铺回原处：用户看到的是"**挪跟没挪一样，只会抖动一下**"，独占全屏的程序还会因为这一来一回掉出全屏。这不只是"少做个无用功"，是**不能做**。判据抽成 `WinIsFullscreen(hwnd)`（窗口矩形 `EqualRect` 显示器 `rcMonitor`），与 `drag.c` 的 `DragBegin` **共用同一个函数** —— 两边标准必须一致，否则会出现"拖动不让动、`C+Q` 却去动"这种自相矛盾的行为。取 `rcMonitor` 而非 `rcWork`：铺满整屏、盖住任务栏那一侧的才算全屏；`MONITOR_DEFAULTTONEAREST` 让坐标悬空的窗口也能落到最近那块屏上，不会因为查不到显示器就误判。查询失败时返回 `FALSE`（当普通窗口处理）：宁可让它挪，也不要因为一次查询失败把功能整个吞掉。
- **放在执行线程**（`act.c` 的 `RunJob`）：`SetWindowPos` 要向对方窗口过程发 `WM_WINDOWPOSCHANGING`/`CHANGED`，对方卡住时同步调用能一直等下去 —— 与按词跳转/探测同一个根因（见 `act.c` 顶部）。非最大化的路径带 `SWP_ASYNCWINDOWPOS`：文档明确"调用线程与窗口所属线程不在同一输入队列时，系统把请求**投递**过去"，本线程不必陪着等。
- **坐标系与 DPI**：本进程**没有声明 DPI 感知**，Windows 会把整个桌面按系统 DPI 统一虚拟化后交给我们 —— `GetCursorPos` / `MonitorFromPoint` / `GetWindowRect` / `SetWindowPos` 用的是**同一个**（本进程的）坐标空间，读与写自洽，所以主副屏缩放比例不同也能落到光标处（依据：MS「High DPI Desktop Application Development on Windows」——"Windows scales and converts DPI-sensitive information from some APIs to the coordinate space of the calling thread"）。将来若给本体声明 Per-Monitor 感知，这段代码不用改：那只是把同一个自洽关系挪到物理像素空间。
- 动作**不发键**：`SINGLE_SHOT`（不进重复节奏、不做松手补齐）与 `NO_SHIFT`（不吃选区修饰）都写在键位表里，`Q` 也不参与"发 3 次"的增强语义。

## 打开程序所在文件夹（`folder.c`）

一句话：`GetForegroundWindow()`（**开火那一刻**的快照）→ 取该进程的映像全路径 → `SHParseDisplayName` 转成绝对 PIDL → `SHOpenFolderAndSelectItems(pidl, 0, NULL, 0)`。

这个模块有**两个入口**，共用同一条 shell 链路与同一条工作线程：

| 入口 | 触发 | 路径来源 |
| --- | --- | --- |
| `FolderOpenRequest(HWND)` | `C+F3` | 该窗口所属进程的映像全路径（UWP 先换真实进程） |
| `FolderRevealPath(const WCHAR*)` | 日志结束气泡被点击 | 调用方给的路径，先过 `FolderResolveTarget` |

两个入口共用一个 `FolderJob`（`{HWND target; WCHAR path[]}`）：`target` 非零走取路径那条，否则走"调用方给的路径"那条，最后都落到 `FolderRevealPidl`。抽成同一个线程过程是为了**不复制那份 shell 调用与错误回报**（`WM_FOLDER_OPEN` 的消息格式、失败码、日志都只有一份）。

`FolderResolveTarget`（纯函数，单测覆盖）解决的是"要选中的东西可能已经不在"：文件在 → 原样返回；**文件不在 → 退回它所在的目录**（至少把文件夹打开，比整个失败有用）；给的就是目录 → 去掉尾部分隔符（`n > 3` 才截，避免把 `C:\` 截成空串）；只有文件名没有目录、或空串 → 失败（没有"所在文件夹"可开）。

为什么是这两个接口：`cidl = 0` 时官方文档写明"传一个**单项**的 PIDL，函数会打开它的父文件夹并选中它"。它就是资源管理器右键「打开文件所在的位置」背后那件事，由 shell 交给**系统当前的默认文件夹处理器**去做 —— 所以**不拼 `explorer.exe /select,` 命令行**（那等于把"文件管理器是谁"写死），用户换第三方文件管理器时这里一行都不用改。
注意这个语义只对**文件**成立：传一个目录进去，是去选中**它上一级里的那个目录**，不是打开它本身 —— 所以"打开某个目录"的路径必须先过 `FolderResolveTarget` 的目录分支。

几个决定与其理由：

- **目标窗口取"开火那一刻"的快照**（`ActJob.hwnd`，在 `main.c` 的 `PostAct` 里填），不是执行时现读 `GetForegroundWindow()`：执行线程是异步的，队列里排在前面的长动作（一次按词跳转能拖到数秒）会让现读拿到**已经切过去的**窗口。与修饰快照（`TRIGF_*`）是同一条规矩。
- **执行在自己的"一次性线程"上**，两条独立理由：① 该调用**同步阻塞**（要等 shell 响应），落在承载钩子的主线程上就是那个老根因（见 `act.c` 顶部）；② **不复用 `act.c` 的动作队列** —— 队列是 FIFO，这条阻塞调用会把排在后面的按键动作一起堵住，而"打开文件夹"是纯发起的动作，没有理由占那条通道。线程 `CreateThread` 之后立刻 `CloseHandle`（线程对象在线程退出时由系统回收），不需要像 `DragLane` / `ImeLane` 那样维护生命周期。
- **线程按 MTA 初始化**（`CoInitializeEx(NULL, COINIT_MULTITHREADED)`）：`CoInitialize` 是**线程级**状态，而 `act.c` 工作线程的套间可能已被 `nav.c` 按 STA 初始化（见其 `CoUp`）；STA 下做同步阻塞的 shell 调用要求该线程泵消息，否则可能死锁 —— MTA 里阻塞调用是允许的。本机实测这条组合三个调用全部 `S_OK`。
- **失败反馈必须绕回主线程**（`WM_FOLDER_OPEN`，`wParam = FOLDER_ERR_*`）：气泡走 `Shell_NotifyIconW` + 主线程的 `g_nid`，工作线程直接调就是对它的跨线程访问。成功**不发**这条消息 —— 文件管理器自己弹出来了，那本身就是反馈。
- **UWP 要先换进程**：UWP 应用在前台时 `GetForegroundWindow()` 给的是宿主 `ApplicationFrameHost.exe` 的顶层窗口，路径指向 `C:\Windows\System32`。真正的程序挂在它下面的 `Windows.UI.Core.CoreWindow` 子窗口上，**那个窗口属于应用自己的进程**，路径就是 `WindowsApps` 里的安装目录。找不到子窗口时**宁可不开**：开 `System32` 并选中 `ApplicationFrameHost.exe` 是确定无用的结果，比"没反应"更容易让人以为程序坏了。
- **目标窗口一律先 `GetAncestor(GA_ROOT)`，并用 `WinIsShellClass` 挡掉桌面/任务栏**（与 `C+Q` 共用同一份判定）。资源管理器窗口本身**不特判**：按字面语义打开的是 `explorer.exe` 所在目录，不是它正在显示的那个目录。
- **`PROC_PATH_MAX` 用 1024 而不是 `MAX_PATH`**：长路径下 260 会截断，而 `QueryFullProcessImageNameW` 支持更长的缓冲区 —— 半截路径解析出来会指向一个不存在的文件（静默失败）。
- **取路径只有一份实现**：`ConfigGetProcessPathByPid` ← `ConfigGetProcessPath(HWND)` ← `ConfigGetProcessName(HWND)`（最后一层抽 basename，供名单匹配）。名单匹配与"打开所在文件夹"要的都只是路径，不该各写一遍 `OpenProcess` + `QueryFullProcessImageNameW`。
- **单测边界**：shell 那一步**测不了**（会真的弹窗口、还要等 explorer 响应），所以它只出现在 `FolderThreadProc` 里；`FolderProcessPathOf` 是同步的、纯本地的，测试直接拿一个真窗口验"解出来的就是本进程 exe 的全路径"（`test_chord` 场景 AH）。
- **已知限制**：目标文件夹已在别处打开时，这个接口仍可能新开一个窗口（不复用已开的那个）。这是接口的既有行为，不是这里的实现选择。

## 按键帮助（`help/help.c`）

一句话：`C+F1` **按住**时，屏幕上浮出一张半透明键位图；松开（F1 或 Caps）即隐。窗口在**独立 exe** 里。

**为什么拆成独立 exe**（与设置程序同一条理由，但更极端）：它要一次性叠上百次绘制（键帽底 + 文字两遍）、常驻一张 32bpp 位图、自己管半透明与生命周期；而本体是**钩子宿主** —— 主线程绝不能为了画图分心（见 `act.c` 顶部那个根因）。拆出去之后，本体只多了一个 `help.c`（拉起 + 报状态），帮助程序那份启动开销与内存也只在按 `C+F1` 时才存在。

几个决定与其理由：

- **不常驻、隐后即退**（隐完留 300ms 缓冲再退，免得"刚松手又按下"来回重启进程）。代价是每次显示 ~20-40ms 冷启动；收益是零后台占用。实测冷启动到可见在几十毫秒量级（GDI+ 起一次 + 画一帧）。
- **显隐靠主程序发消息，而且要重试**。冷启动意味着"按下 30ms 就松手"这种操作会让 SHOW 与 HIDE **都落在窗口出生之前** —— 窗口起来后不知道该显示还是该消失。两边的对策缺一不可：
  · 帮助 exe 启动后**先建隐藏窗口**，等主程序告诉它状态；1.5 秒等不到就自己退出（防呆，见 `TID_ARMED`）。
  · 主程序把"期望状态"记下来，用 40ms 的定时器反复对账直到送达或超时（1s）。状态幂等，重发没有副作用。
  另：**寿命由心跳兜着** —— 显示期间主程序每 200ms 发一条 KA，帮助 exe 800ms 收不到就自己退。这一条取代了原先的"每秒看一眼主程序窗口在不在"与"显示超 3 分钟自动收起"，因为它盯的是更根本的事实（**"我还被需要吗"**）：HIDE 丢了、主程序被强杀、主程序卡住不动，在别处是三种场景、在这里是同一件事 —— 喂狗停了。代价只是显示期间每 200ms 一次 `PostMessage`（找不到窗口就什么都不做）。手动双击那份没有喂狗的人，所以仍自己兜 3 分钟（`TID_LIFE` 只在非 `--hold` 下启动）。
- **文字用 GDI+ 的灰阶抗锯齿（`TextRenderingHintAntiAliasGridFit`），刻意不上 ClearType**。理由是本窗口的性质：它是**逐像素 alpha 的半透明浮层**，而 ClearType 是次像素渲染 —— 它对"文字下面是什么颜色"有假设，在带透明背景的位图上支持并不完美：会留下**彩色镶边**（看着像锯齿），深底亮字还会 blooming（观感"莫名其妙地粗"）。四种渲染并排实测过（同一块 DIB、同一字号：GDI+ GridFit / GDI+ AntiAlias / GDI ClearType / GDI ANTIALIASED）：ClearType 最粗且有彩边，ANTIALIASED 偏细软，**GDI+ 的 AntiAliasGridFit 在深底亮字上最锐利、且完全没有彩边**。
  ✗ 别加 `SetTextContrast(5)`：中文密集笔画会糊成块，"增强"两个字会粘在一起。
- ★★ **去掉 ClearType 之后，"清不清晰"就只剩字号这一个变量了** —— 而字号的上限是**几何**的：键帽内宽 ÷ 每行字数。所以：
  · 键帽缝隙（`CAP_GAP_K`）与标签留边（`LABEL_PAD_K`）收到最小，把空间让给字号；
  · 字号是**逐键帽各定各的**（`PickFuncSizes`）：短文案的键用目标字号，长文案的键（F3 的"打开|程序目录"、反引号的"记录日志"）自动降一档 —— 长文案不再把所有键拖小，文案也就不必为字号让路；
  · 实现是 `AllLabelsFit` 的按键版 `LabelLinesFit`（按 `|` 切段，每段都要装得下），从目标值往下找到第一个全通过的；绘制侧用一个小缓存按字号取 `Font`（档位最多三四档）。
  （GDI+ 的 `MeasureString` 每侧会多算 1/6 em，是它的既有行为 —— 直接拿它当判据会让字号白白小一号，所以 `TextWidth` 按 `em/3` 把这份 padding 补回来。）
- **逐像素 alpha，不是整窗调透明度**。`SetLayeredWindowAttributes(LWA_ALPHA)` 会把键帽、文字一起变淡（观感发虚），而这里要的是"背板半透明、内容实心"。所以走 32bpp PARGB DIB + `UpdateLayeredWindow(ULW_ALPHA)`，做法沿用本机 IMEIndicator 的 `overlay.c`（同一套 `WS_EX_LAYERED | NOACTIVATE | TOPMOST | TOOLWINDOW`）。没有要 `WS_EX_TRANSPARENT`：窗口需要收点击（点一下关闭）。
- **不抢焦点是硬要求，也决定了关闭方式**。窗口带 `WS_EX_NOACTIVATE`、显示用 `SW_SHOWNOACTIVATE` —— 目的是"按着看的时候还能继续在原程序里操作"。代价是它永远拿不到键盘焦点，**`Esc` 关不掉**：所以关闭方式只有"松开键"与"点一下窗口"。
- **键位布局按 ANSI 104 标准**（15u 主键区、功能行 Esc 与 F1 之间隔 1u、F 键每四个一组各隔 0.5u、功能行与数字行之间 0.25u），取自 keyboard-layout-editor 的 ANSI-104 定义 —— 只有位置对得上真键盘，这张图才能当"肌肉记忆的对照表"用。不含小键盘：它在 CapsEnhance 里零映射，画上去只是让窗口宽出三成。
- **键帽两行：上=原键名、下=功能名**。功能名**不替代**键名 —— 先认出"这是哪个键"、再看它做什么，两行都在键帽里。没有功能的键只留键名并淡化，所以图仍能当"这是一把标准键盘"看。
- **文案只有一份**：功能名来自 `keymap_table.h` 的 `label`（与日志用的 `name` 分开：日志要 `←(J)`，图上只要 `←`）。修饰键（Caps / D / 左 Alt）与诊断键（反引号）不是"触发键 → 动作"那一类，它们的文案在 `help.c` 的 `LabelOfVk` 里单独给出，但反引号那条**借用的仍是键位表里 `ACT_PROBE` 的 `label`**（PROBE_KEY 由 `hook.c` 特殊处理，表里 vk=0）。
- **长文案的断点由数据决定**：`label` 里的 `|` 就是断行点（`"打开|程序目录"`）。中文没有词间空格，让程序按宽度自动断会把"打开程序目录"切成"打开程 / 序目录"——语义上难看。没写 `|` 的才走按宽度自动折行。
- **尺寸与字号全部按 DPI 缩放**。本进程是 Per-Monitor V2，坐标与位图都是**物理**像素，而"多大算合适"是**逻辑**尺寸问题：4K@200% 的物理工作区是 3840x2160，若把单位长度 u 的上限写成 78 物理像素，图上每个键就只有 39 逻辑像素 —— 比 1080p 屏上还小一半，字自然又小又糊。所以基准刻度（u=50、边距 24/26/40/16、底部行高 24、四个字号）统一乘 `dpi/96`，任何缩放率下看起来一样大。整套刻度是**等比的**，改一个 `u` 就整体放大/缩小。
  ★ 这些布局量由 `FitUnit` **算一次放进全局**（`g_pad / g_title / g_gap / g_foot / g_fsName..Foot`），绘制侧不再自己写第二份常量 —— 这里踩过两个真 bug：一次是开窗按 u=78、绘制按 u=64（四周留了一圈空白），一次是标题与底部字号写死成 17px/13px（高分屏上不跟着放大）。
  ★ 功能名的字号是**几何约束**出来的（每颗键帽的内宽 ÷ 自己的每行字数），跟 u 只是间接关系 —— 所以 `FitUnit` 给的那个 `u × 0.28` 只是"上限目标"，真实值由 `PickFuncSizes` 逐键帽实测往下找。字号一律**取整**：非整数像素下同一行里每个字的 hint 结果不一致（有的胖有的瘦），看着就是"字体怪"。
- **键帽上的颜色按对比度选，不是凭感觉挑亮/暗**。WCAG 的 AA 线是 4.5:1，十几像素的灰阶抗锯齿中文低于它就开始"看不清"：深蓝底 `#0C447C` 上键名用 `#C7DFF7`（7.3:1）；琥珀底原来是 `#BA7517`，而**那个亮度上任何浅色都到不了 4.5:1**（纯白也只有 3.8:1）—— 所以"橙色键的字母看不清"不是选色问题，是底色太亮，压到 `#96601A` 之后才站得住。
- **键名位置统一在键帽上部**：未映射的键以前是居中的，于是同一行里两种键名的基线高低不一，扫过去是跳的。
- ★ **GDI+ 的 `NoWrap` 在文字宽于矩形时是直接裁掉**（真机上 F3 的"程序目录"就这么变成了"程序目"—— 字直接消失，最难查）。所以 `DrawLine` 居中时把矩形**左右各放宽 10%**（对称，不改变居中位置），并且字号按实测留足余量。
- **字体写死"微软雅黑 UI"，不跟随系统默认**：系统默认 UI 字体（`SPI_GETNONCLIENTMETRICS` 的 `lfMessageFont`）通常是 Segoe UI，中文会掉到回退字形（笔画细、像点阵），而这图上大半是中文 —— 拿系统默认只会更难看。雅黑 UI 是 Win8+ 自带的 UI 版，字形与系统界面一致；取不到再退标准雅黑。
- **底部两栏**列出不是"某个键"的功能（滚轮、单击、鼠标拖动）。键名区的宽度取**本栏最长键名的实测宽度** + 一个间隔，而不是"半个栏宽" —— 那样键名贴最左、说明从栏中间开始，一行字会被扯成断开的两半。
- **三条"单击 Caps / 左 Shift / 右 Shift"的文案来自配置文件**（`CapsEnhance.ini` 的 `ImeCapsMode / ImeLShiftMode / ImeRShiftMode`：0 不处理 / 1 切中文 / 2 切英文）。写死一个"切中文"在这里，用户把配置一改图就开始撒谎。
- **读 ini 不用 `GetPrivateProfileIntW`**：本 ini 是 **UTF-8（带 BOM）**，而 Windows 的 profile API 会把带 BOM 的 UTF-8 当成 ANSI 认，BOM 那三个字节会粘在第一行的段名前面。这里只关心三个纯 ASCII 的键名与它们的十进制值，按字节扫一遍就够，也不受编码 / BOM / API 缓存那些怪癖影响；读不到就保持默认（与 `config.c` 同一条规矩）。
- **测试边界**：窗口像素测不了（要真人按住键）。能离线钉住的是"键位接线 + 寿命语义 + 每条动作都有图上文案"（`test_chord` 场景 AI，文案那条靠遍历共享的键位表）。跨进程那份契约用一次性工具单独验过：`--hold` 起来时不显示、发 SHOW 出现、持续喂 KA 则一直显示、**停喂 800ms 后自己消失**、发 HIDE 消失并退出、手动模式下不吃心跳判据。渲染效果靠一次性抓图工具（屏幕 DC + `BitBlt`，`PrintWindow` 抓不到分层窗口）对着真机看。

## 坐标空间：为什么主进程必须声明 DPI 感知

**一句话**：低级鼠标钩子给的 `MSLLHOOKSTRUCT.pt` **永远是物理像素**（官方定义就是
"per-monitor-aware screen coordinates"），所以本进程也必须活在物理空间 ——
`WinMain` 第一件事就是 `WinInitDpiAwareness()`（Per-Monitor V2，AltSnap 的清单里也是这么声明的）。

不声明会怎样（**这曾经是一个真 bug**，用户报的两个症状都由它引起）：

| | 钩子给的坐标 | 本进程 API 的坐标 |
|---|---|---|
| 声明感知后 | 物理 (1351,613) | 物理 (1351,613) ✓ 同一空间 |
| 不声明 | 物理 (1351,613) | 系统按 96DPI **虚拟化** (772,350) ✗ 差一个缩放比 |

本机实测（真实 2558x1319 @175%，虚拟化后 1462x754）。于是：

- `WindowFromPoint(钩子坐标)` 指向**别的地方** → 常常命中那块位置上的另一个窗口（多半是
  前台/最大的那个）→ 表现成"**只能拖有焦点的窗口**"；
- 光标位移是物理量（1.75 倍）却加在虚拟坐标上 → 窗口比光标**多跑 75%** → 表现成
  "**拖动时窗口和光标差很远**"；全屏窗口在副屏上还会因为虚拟矩形错位而**没被识别成全屏**。

★ **自检不能拿 `GetPhysicalCursorPos` 当判据**（我第一版就这么写错）：实测它对不感知的
进程**同样虚拟化** —— 与 `GetCursorPos` 一起返回 772,350，两边一起变，看起来"一致"，
恰好把这个 bug 放过去。有效判据是**显示模式尺寸**：`EnumDisplaySettings` 的 `dmPelsWidth`
**不被虚拟化**（两种模式下都是 2558），与本进程的 `SM_CXSCREEN` 一比就知道
（1462 vs 2558 = 虚拟化生效）。见 `WinCoordSpaceConsistent()`。

自检结果写在**启动基线**里（`C + \`` 记录模式下可见）：

```
DPI 感知 = 每显示器V2(PerMonitorV2)  坐标空间 = 物理(与钩子一致)
```

排查"拖动错位/指错窗口"时，**先看这一行**：显示"虚拟化(与钩子不一致)"就说明感知没生效。

★ 另一个实测坑：`GetAwarenessFromDpiAwarenessContext` 对 **PerMonitor 与 PerMonitorV2 都返回 2**
（V2 的差别在行为上，不在这个枚举里）。要区分 V2 必须用 `AreDpiAwarenessContextsEqual`。
（`WinDpiAwarenessName()` 就是按这个顺序判的。）

测试与保险丝：
- `test/dpitest.c`（独立 exe，**必须在没有任何窗口时跑** —— 声明感知的前提）：断言声明后
  坐标空间一致、且不再是"不感知"。在 100% 缩放的机器上恒真，在缩放机器上就是那根保险丝。
- `test/restarttest.c` 直接查**产品进程**的感知级别（`GetProcessDpiAwareness`）：
  一旦 `WinMain` 里那句初始化被删掉，这条断言立刻变红。

## Caps+左键拖动窗口（`drag.c`）

按住 Caps 时按下左键：接管**光标下的顶层窗口**跟着鼠标走。交互借鉴 AltSnap（它默认用 Alt 键做同一件事），结构与本项目对齐：判定在鼠标钩子，执行在专用线程。

- **判定必须在按下那一刻**：吞不吞这次左键只能当场决定（事后发现该放行，down 已经没了）。所以黑名单/桌面/任务栏/自己的窗口/全屏/最小化这些"不接管"的检查都写在 `DragBegin` 里，钩子只调它一次 —— `OpenProcess`/`GetClassName` 这类本地查询可以接受，但**不做跨进程消息**。
- **全屏判定复用 `winmove.c` 的 `WinIsFullscreen`**（模块间零依赖地被 `winmove.c` 提供）：`C+Q` 那边也要拦同样的窗口，两边各写一份就会漂移。注意 `DragBegin` 里原来那次 `GetWindowRect` 是与全屏判定合用的，改成函数调用之后，"普通窗口的抓取基准"要**单独再查一次**矩形 —— 但必须在 `EnterCriticalSection` **之前**查好，否则取不到就只能带着没释的锁 `return`（那是难查的死锁）。这条路径是"用户按下 Caps+左键"的一次性开销，不在拖动的逐帧循环里。
- **吞放配对**：接管就吞掉 down，up 也必须吞（`g_dragSwallowUp`，与键盘的 `g_swallowVk` 同一条规矩）。Caps 中途松开导致拖拽结束也**不清**这个标志 —— 那次 up 仍要吞，否则漏一个孤立抬起给目标程序。
- **"最新点 wins" 的节流**：钩子每帧只做一次临界区写 + SetEvent，执行线程取**最新**点应用一次 —— 与 AltSnap 的 MoveRate/RezTimer 目的相同，但不需要猜采样率；中间帧自然合并。
- **不穿透点击**：Caps+左键按下去就是拖，不传给目标程序（AltSnap 默认 PiercingClick=0 同为不穿透）。没接管（黑名单等）时左键原样透传，且仍要打断持续滚动 —— 这条语义不能因为新功能丢掉。
- **拖出阈值（对齐 AltSnap 的 `DragThreshold=1` + `DragOutThresholdPx=20`）**：
   **只对最大化窗口**生效 —— 按下后要先拖出 `DRAG_OUT_THRESHOLD_PX`(20px) 才真正
   "还原 + 跟随"，阈值内（包括"点一下"完全没动）**什么都不做**。
   为什么必须有：最大化窗口一还原就变小，若"按下即还原"，`Caps+左键`**点一下**就会
   把窗口缩小 —— 这是本功能最刺眼的问题。实现上把"发 `SC_RESTORE`"从 `DragBegin`
   推迟到执行线程"越阈值"那一刻（钩子线程里只记按下点），并记录模式下的日志
   `越过拖出阈值(20px)` / `结束（未越过拖出阈值，窗口未动）`。
   判据是**方框**（任一轴超过即算），与 AltSnap 的 `IsPtDragOut` 同义 —— 用半径会让
   斜向拖动比正上下左右更难触发。
   （AltSnap 的 `DragThreshold`：0=不设；1=只对最大化/已吸附窗口设（默认）；2=总是设；
   3=缩放时也设。我们还没有"吸附"，所以等价于 1。）

- **最大化窗口先异步还原**：还原用 `PostMessage(WM_SYSCOMMAND, SC_RESTORE)`（**异步**，不能在钩子线程里等），执行线程**有界轮询** `IsZoomed` 等它落地（≤200ms），落地后才取"还原矩形"当抓取基准、并把光标基准重新锚到"现在"（否则还原期间鼠标动过的距离会叠加，窗口会跳）。等不到就收手 —— 宁可这次不拖，也别挪去错的地方。
- **黑名单 = 两份**（`[DragWindowBlacklist]` 按窗口类名 / `[DragProcessBlacklist]` 按进程名），与 AltSnap 的 `Windows` / `Processes` 两条一一对应，各自独立缺省回落（谁的段没写就用谁的内置默认，都逐条取自 AltSnap）。命中任一份即不接管。
  **不支持标题维度**：取另一个进程的标题要发 `WM_GETTEXT`（跨进程 IPC），而判定发生在鼠标钩子上；AltSnap 的默认条目每条都带类名或进程名，默认语义仍完整。
  两份名单的空判定分开做：类名是本地调用（便宜），进程名要 `OpenProcess`（与 `[AutoDisable]` 同一条路）—— 名单为空时不该付这个代价。

## 单键切换输入法（`ime.c`）

单击 `Caps` / 左 `Shift` / 右 `Shift` 把输入法**强制**切到固定一边（`ImeCapsMode` / `ImeLShiftMode` / `ImeRShiftMode`，`0` 不处理 / `1` 中文 / `2` 英文）。协议与"先转换模式后 open"的顺序借鉴 KBLAutoSwitch 与 InputTip。

**判定在钩子、执行在线程**：切一次要向别的进程的 IME 窗口发最多 3 条 `WM_IME_CONTROL`（每条 `SendMessageTimeout` 200ms），外加可能的布局切换 + 落地等待 —— 放在键盘钩子里会直接把钩子冻住（见[架构总览](#架构总览)）。所以 `hook.c` 只做**单击判定**并调 `ImeRequest()`（一次赋值 + SetEvent），真正干活在 `ime.c` 的专用线程。

**"单击"的判定，两个键不一样**（这是本功能最容易写错的地方）：

| | 判据 | 为什么 |
| --- | --- | --- |
| `Caps` | 本次 Caps 会话内**没有触发过任何动作**，松手即算 | Caps 是**和弦首键**，本来就不承担别的作用，无需时长限制（按住发呆再松开仍该切换） |
| `Shift` | 期间**没按别的键** **且** 按下时长 ≤ `IME_TAP_MS`(300ms) | Shift 是**系统也在用**的真修饰键：`Shift+A`、`Shift+拖动`、以及不少输入法自己的 `Shift` 切中英，都必须是"短按且没组合"才轮得到我们 |

实现上：`s_capsUsed` 在 PROBE_KEY / 触发键 / 鼠标各键 / 有效滚轮处置真（Caps 松手时看它）；`s_shiftArmed` 在按下某个 Shift 时置真、按下任何**其它**键或长按超时即失效。两个 Shift 同按直接取消判定（`Shift` 本身就是组合的一部分）。

**执行侧（`ImeRunKey`）按这个顺序收口**：

1. 模式为 `IME_MODE_OFF` → 钩子侧就不调 `ImeRequest`（**零开销**，见上一节）；
2. **无前台窗口** → 返回（没有目标，切了也是切到桌面）；
3. **前台是英文键盘（主语言 `0x09`）** → 返回，**三个键都算，Caps 也一样**；
4. `ConfigIsAutoDisabled(前台窗口)` → 返回（三个键与"整段不介入"共用同一份 `[AutoDisable]`，同一语义）；
5. 取 `ImmGetDefaultIMEWnd`，设 `IMC_SETCONVERSIONMODE` 的 `IME_CMODE_NATIVE` 位 → 再设 `IMC_SETOPENSTATUS`；最后**回读**校验并写日志。

第 3 条是本功能与 KBLAutoSwitch / InputTip 的**分道处**：它们会把键盘布局切到中文（InputTip 甚至"没装就装一个"），本项目**不切布局**。理由见下。

几条刻意的取舍：

- **只动 `IME_CMODE_NATIVE` 一位，不用掩码清位**（KBLAutoSwitch 用 `2046` 掩码）：那会顺手清掉用户的全角/符号等其它转换模式位。
- **先转换模式、后 open**：部分输入法在 `open=0` 时拒绝改转换模式。
- **★ 不切键盘布局，英文键盘下三个键一律不处理**：早期实现会替用户把布局换成**已安装**的中文键盘（只查 `GetKeyboardLayoutList`、不调 `LoadKeyboardLayout`），但"替用户换键盘"这件事本身就是改他的输入环境，与"不写注册表、不改系统设置"的边界相冲突；更实际的问题是用户**停在英文键盘上**时，按一下 Caps 会被悄悄换走键盘 —— 那不是他要的。所以现在英文键盘下就是没反应，日志里留一条 `前台是英文键盘` 说明原因。
- **单槽 latest-wins，不排队**：切换是幂等的，排队只会让结果**更晚**到达（连按两下得到的是延迟后的同一结果）。

测试分工：`test_chord.c` 的场景 AG 用伪造按键序列覆盖**判定**（谁算单击、谁不算），`test_config.c` 覆盖三个模式值的解析/钳制/写回/模板/升级。`ime.c` 的跨进程 IME 通信**不进单测** —— 它依赖机器上装了什么输入法，没法在本机给出稳定断言。

## 滚轮三路实现要点

按住 `C` 时滚轮请求在钩子里只做一次**投递**（`WM_WHEEL_HACCEL` / `WM_WHEEL_ENH` / `WM_WHEEL_ACCEL`），状态机与注入都在 `act.c` 的独立通道 + 独立线程里跑。三路共用配置的判定顺序：**真实 `Shift` → 横向；增强模式（Alt/D）→ 持续滚动；否则 → 快速滚动**。

| 路 | 物理格处理 | 语义 |
| --- | --- | --- |
| 横向（`C+Shift+滚轮`） | **吞掉**（返回 1） | 物理滚轮送出的是**纵向**事件，放行就"横一下、纵一下"混滚 |
| 持续滚动（`C+Alt/D+滚轮`） | **吞掉**（返回 1） | 滚轮是控制杆：同向滚只有"提速"、反向滚只有"打断"；通道被激活立刻补发第一格（即时反馈来自我们的注入） |
| 快速滚动（`C+滚轮`） | **放行**（照常送达） | 是"加强"不是"替换"——系统滚一格 + 我们补几格 |

**倍数量与毫秒/格不混用**：两者是两种量，既不能比较也不能互相约束。曾试图统一成一个值（"放大速度 = 自动滚动上限"），结果两边都别扭；现在各管一段（`test_config` 直接断言）。

**实现只做输入注入**，不改系统设置、不写注册表：

- **不碰** `SPI_SETWHEELSCROLLLINES`，也不模拟按键（`PageDown` 之类），而是注入**标准滚轮刻度**（或其"零头"）。
- 用低级鼠标钩子而不是 Raw Input：**必须能认出"这个滚轮是自己注入的"**（`LLMHF_INJECTED`）——Raw Input 没有注入标记，放大后的滚轮会再触发一次，形成无限放大。若 `WH_MOUSE_LL` 装不上，主映射照常工作，托盘提示显示"滚轮不可用"。
- **逐格发、每格间隔 2ms**，不是一个事件塞一个大 delta。实测：一次 `SendInput` 批 3 个刻度 → 目标只收到 1 条、`delta=360`，`+120` 与 `-120` 同批更会合成 `delta=0`；3 个事件间隔 2ms 逐个发 → 收到 3 条、每条 `delta=120`。不少程序只看 delta 符号、每条只滚一格（Blender 为此专门拆大 delta）。
- **注入跑在专用线程上**（不是主线程）：主线程一旦不在等消息状态，钩子事件会被系统直接跳过（见[架构总览](#架构总览)）。
- 松开 `C` 时把**还没发完**的请求丢掉，不会出现"手松了还在滚"的尾流。注入被系统拒绝（如目标窗口完整性级别更高）时，横向 / 持续滚动那一路会丢这一格。

### 持续滚动的速度与粒度

- **速度靠"每格之间的间隔"表达**，而不是"每个节拍补一撮"（后者从第 2 档起就是"一小串脉冲 + 一大段静默"，看上去在抖）；变速不打断当前节拍，下一拍才生效。
- 速度在 `AutoScrollInterval`（起步）与 `AutoScrollFastMs`（上限）之间按**几何**（速度的对数）铺开 **6 档**——每档倍率相同、手感均匀；两端相等则退化为恒定速度。若按线性铺开，两端拉开时第 1→2 档就是几十倍（"再滚一下直接飞出去"）。
- **粒度默认是"小数刻度"**，例外由 **[NoSmoothScroll] 名单**给出：默认注入的不是"整格 120"而是**不足一格的小刻度**、次数更密（每 40ms 一次），速度不变（`delta ÷ 节拍` 一样），手感像触控板连续滑动。Windows 本来就允许 `zDelta` 是 `WHEEL_DELTA`（120）的"倍数或约数"——程序可累积或按小数刻度滚动，所以这是**触控板同款的滚动事件**。
  > 真正的触控板 / 手势（`WM_POINTER`、Direct Manipulation）无法从用户态注入（需 HID 驱动），小数刻度是能做到"连续滚动"的正规途径。个别老程序不累积小数刻度（完全不动），把它的进程名写进 `[NoSmoothScroll]` 即退回整格。
  >
  > 它以前是一个全局布尔 `AutoScrollSmooth`，已删除：要表达的是"个别程序的行为"，做成全局开关等于让**所有**程序一起陪着退化，而用户往往要滚的正是那一个程序。判定在**启动持续滚动那一刻**做一次（`ActAutoScrollSetNoSmooth`）：查前台进程名要 `OpenProcess`，不能每拍都做。

**终止条件**（2026-09-11 两版改完）：

| 动作 | 结果 |
| --- | --- |
| 反向滚（且还按着 `C+Alt/D`） | 终止 + 速度清零 |
| **新按下**一个键（含修饰键、含被吞掉的键） | **终止**（**系统自动重复不算**） |
| **鼠标键按下**（左 / 右 / 中 / X） | **终止**（抬起不算） |
| **不带和弦的滚轮**（没按 C、只按 C 的放大档、C+Shift 横向档；纵轴横轴都算） | **终止** |
| 鼠标**移动** | 不终止（否则手一抖就停） |
| `Caps+Alt/D+滚轮`（**唯一的控制杆**；纵轴、横轴、`delta=0` 占位帧都算） | 不终止，只调速 |
| 超过 **10 分钟**没有调速 | **自动终止**（防止人走开了还在滚） |
| 托盘"暂停映射" / 退出 / 重启 | 终止 |

> **什么叫"新输入"**（第二版修正，两处都踩过；都留了日志）：
> ① **系统自动重复不算**。按住任意键时重复 keydown 源源不断；把重复当"新输入"，就会"滚轮一动、第一格刚出去就被自己按住的键打断"——症状正是**滚一下就停**。判据是"此键此前**不是**按下状态"（钩子自维护的物理按键表，与长按重复去抖同源）。
> ② **按着和弦时的滚轮整只手势都算控制杆**：横向轴（触控板双指滑动同报两轴）与 `delta=0` 占位帧过去会落到"新输入→打断"，同样表现为**滚一下就停**。现在它们要么被当作控制杆吞掉（和弦按着），要么在没按和弦时才按新输入处理。
> 为什么 10 分钟上限：松手后滚动由自己驱动，万一人离开或钩子被系统摘掉，就没东西能停它了。计时从最后一次调速起算。
> 一句话：**新按一下键（或鼠标键）就停；只有 `Caps+Alt+滚轮` 是"调速"而不是"新动作"。**

**每次终止都会在记录模式下写一行日志**（`持续滚动：终止（原因 …, 已注入 N 拍）`，含谁停的、键码 / 滚轮增量 / 鼠标消息号，以及本次已注入拍数）。终止条件全在钩子 / act 侧，症状出现时现场什么都不剩，所以要专门留行：排查时先 `C + \`` 开始记录再复现。

**默认速度是按阅读速度反推的，不是手感试的**（早期 `120→300→500→4000` 改四轮都还偏快）。换算假设：Windows 默认"每次滚 3 行"、一行 45 字，`字/分钟 ≈ 135000 ÷ AutoScrollInterval`：`120→67500` 字/分、`4000→2025` 字/分（仍 4~7 倍于人）、`24000→338` 字/分（通用默读偏慢半区）、`60000→135` 字/分（技术精读）。**当前缺省 1500 已不按阅读速度定**——持续滚动现在是"按住快速浏览"的工具（要慢读调大 `AutoScrollInterval` 或直接普通滚轮；想回到"读文档刚刚好"设回 24000）。

### 横向滚动细节

`Caps+Shift+滚轮` = 横向滚动，速度由 `WheelHScrollMul` 控制，默认 `1`（一滚换一次标准横向滚动 `±120`，与系统原生一致）；`0` = 关闭；上限 16。只用**真实 Shift**（按住 C 时 Shift 被本程序屏蔽不外泄，只用于选轴向）。**方向与滚轮上下相反，跟系统约定一致**（滚轮上 = 左，下 = 右）——沿用浏览器 / 资源管理器 / 表格的既定方向，用户不必重建肌肉记忆。轴向优先级 `Shift` **高于**纵向那两档。

### 快速滚动细节

"按住 C 时滚轮更远"：每个物理刻度**原样送达**，再补 `N-1` 个同值刻度，一格 = `N` 格（`WheelScrollMul`，默认 3）。`N=0/1` = 不放大；上限 16（单次最多补 15 格，每格间隔 2ms）；补发在专用线程执行。`N=2` 只补 1 格、无间隔等待，手感与系统原生一致；`N≥3` 要隔 2ms 逐格补发，滚动时能感到轻微卡顿。

## 配置项的设计与新增清单

**设计说明**：该项目配置项**不提供增强键 / 选区键开关**（`Alt/D`、`F`）。它们曾短暂做配置项（`EnhanceKeys` / `ShiftKeys`），当前版已去掉并回退（配置文件里写这两个键名会忽略）。原因：它们属于和弦语法，改它等于改功能，不该是暴露给用户的旋钮。

新增 / 修改一个配置项牵扯到**八处**，漏一处不会编译报错，只会静默不一致（历史上"默认值从 2 改成 3"就漏改过三处文案）：

1. `config.c` 顶部：**常量**（`*_DEFAULT` / 范围上下限）——默认值只在此定值；
2. `config.c` 的 `ConfigLoadFrom`：静态初值 + 解析分支（钳制走 `Clamp*`，不另写）；
3. `config.c` 的 **ini 模板**（`kTemplate`，文件不存在时写出）；
4. `config.c` 的 **`kUpgrades` 表**（老配置补齐，用 `STR(常量)` 拼；设置程序写回缺失键时复用的也是这份注释块）；
5. `cap.h` 的 `ConfigGet*` 声明 + `config.c` 实现；
6. `cap.h` 的 **`ConfigSet*`** 声明 + `config.c` 实现（设置程序改值用；与 Get 成对，漏了就是"界面改不动它"）；
7. `config.c` 的 `GeneralValues()`（写回时的"键 = 值"清单：`key` 小写用于匹配、`name` 是写进文件的形态）；
8. `settings/settings.c` 的 `kFields` 表（一行 = 一个控件）+ Load / Save 的两个分支，以及 README / 本文的说明。

**改默认值时务必全局搜那个数值**：注释、模板、`kUpgrades`、测试注释与**断言消息**里都可能写死它。"键齐全时升级不改动文件"的 fixture 由 `ConfigUpgradeKeyName()` 现读现生成，所以那条用例不会因加配置项假失败。

**新增一份名单**则要动四处（现有五份 ——  /  /  /  / `[DragProcessBlacklist]` —— 都走这个机制）：

1. `cap.h` 的 `CFG_LIST_*` 编号 + `ConfigMatchList` / `ConfigIsXxx` 声明；
2. `config.c` 的 `CfgListId` 枚举（值取自 `CFG_LIST_*`，不另写数字）；
3. `config.c` 的 `CfgSec` 枚举 + `SecList()` + 段名解析（`_wcsicmp`）；
4. ini 模板里补一段（带注释说明），以及 README / 本文的名单段说明。

名单是"加了索引的数组"（`g_names[list][i]`），不是"一份数组 + 几个常量" —— 它们的语义完全不同，共用一份就等于任一命中都会触发所有行为。

**各配置项语义去重来源**：以 `config.c` 的常量与模板为准；本文不再重复逐条解释（见 README 的配置表）。仅补充两点边界：

- `AutoScrollFastMs` **必须小于** `AutoScrollInterval` 才有提速空间（毫秒越小越快）；写反不会崩，只是阶梯退化成恒定速度。
- `WheelHScrollMul` 横向**不做**小数刻度平滑（它的语义就是"一滚换一列"，整数格更符合直觉）。

## 诊断日志：覆盖"输入 → 决策 → 输出回读"，而不是只记决策

踩过一次很典型的坑：EmEditor 里跳词后按 J 没反应，而且只有它有这问题，
而当时的日志**每一行都是成功的**：

```
path=Edit len=73 caret=58 -> steps=7 tgt=51
-> 直接 EM_SETSEL [51,51] 已校验
```

记录不可谓不详细，但全在**决策层**。用户感知的"没反应"发生在下游（注入 → 目标
程序是否认账），那一侧**一行都没有**。于是同一个现象至少有三种成因 —— ①请求没
到 ②到了但被拦 ③发了对方不认 —— 日志一条都排除不了，只能靠猜（前两轮确实猜错了
两次）。

补上观测点之后，**第一次运行就定案**（`<<< 发了但光标没动`）。所以问题不是
"日志不够详细"，而是这条链上根本没有观测点。三个具体缺失：

1. **输入侧**：钩子到底收到了哪个键、当时和弦是什么状态 → `[和弦] X 按下/抬起`。
2. **输出侧回读**：注入**前后各读一次目标程序的真实状态**（光标在哪）→
   `[注入] ←(J) -> vk=0x25 光标 51 -> 51  <<< 发了但光标没动`。
   相差一格也说明"对方执行了"，读不动则说明"发了但没认" —— 这一条就把三种成因
   分开了。
3. **跨模块的因果**：副作用的成因（`EM_SETSEL` 置位）与症状（**下一次**按键）在
   日志上相隔 1.2 秒、还分属 `nav.c` 与 `hook.c`。人眼做不了这种跨模块跨时间的
   关联，必须有一个"同时知道上一次做了什么、这一次按了什么"的观测点。

两条通用规则：

- **"成功"只说明我们发出去了，不说明对方接受了。** 凡是"我们发了但对方可能不
  理"的动作（注入按键 / 跨进程消息 / COM 调用），都应在动作前后各读一次对方的
  真实状态并记进日志。
- **不要用"相邻两次观测的差值"代替"每一次的回读"。** 曾经拿"下一次跳词读到的
  caret 变了"推断"上一次按 J 生效了"，而那个差值完全可以由用户自己的手动操作
  造成 —— 实测就被这么误导过（caret 51→50 被当成"J 生效"的证据，其实是他自己
  按的）。逐次配对才不会被无关操作污染。

还有一个附带结论：记录模式是**手动开关**的，所以"出问题的瞬间没开记录"就等于
没有证据。这也是打点要尽量**便宜**（几行 `fprintf` + 一次读状态）的理由 ——
便宜才敢常开。

## 排障速查 / 坑点速记

跨模块、容易反复踩的坑集中于此，细节见对应章节。命名以代码为准（`src/*.c` / `src/*.h`）。

### 线程 / 钩子
- **`volatile` ≠ 线程安全**：`volatile` 只防"编译器优化"，不建立 happens-before、也不保证原子性 —— 跨线程标志必须 `std::atomic`（本项目只有 `g_recording` 与 `g_injectedDown` 属此类；其余 `volatile` 标志都是主线程内的，真正的用途是防低级钩子回调被编译器"提出循环"，见[跨线程安全](#跨线程安全与和弦引擎要点)）。
- **主线程绝不能离开"等消息"状态**：`WH_*_LL` 回调跑在安装它的线程（主线程）。主线程里 `Sleep` / 同步跨进程 IPC（`SMTO_BLOCK`）/ COM 往返 / 模态弹窗 → 钩子被系统**静默摘除**（"莫名失效"且无日志）。凡阻塞一律搬 `act.c` 的工作线程（滚轮另有独立线程）。
- **测试里别 `Sleep` 干等**：系统对 LL 钩子"直接跳过"而非补发，干等会**永久漏记**；必须 `MsgWaitForMultipleObjects` 一边泵消息一边等。
- **系统会合并未派发的滚轮事件**：3×120 变 1 条 360；`+120`/`-120` 同批合成 0。要逐格必须逐格发、每格隔 2ms。

### 持续滚动（act.c）
- **写序竞态**：`ActAutoScrollWheel` 里 `dir` / `gear` / `deadline` **先写**、`active` **最后置**——工作线程看到 `active` 才用 `dir`，反过来会读到 `active=1, dir=0` 中间态 → 刚启动就自己停。
- **`dir == 0` 的防御分支不能只清 `running`**：`active` 仍为 1 → 下一轮跳过空闲等待 → **没有等待的死循环（CPU 空转）**；必须显式 `ActAutoScrollStop()`。
- **超时是"钩子被摘掉"时的最后一道闸**：旧代码靠工作线程读 `g_cMod`/`ModeDown` 自查，钩子一被摘除那两个值永远是"还按着" → 无限滚。死线只存 **32 位**（取 `GetTickCount64` 低 32 位，回绕比较，别撕裂）。
- **倍数量与毫秒/格不混用**：`AutoScrollFastMs` 必须 **<** `AutoScrollInterval`，写反 → 阶梯静默退化为恒速（详见[滚轮三路实现要点](#滚轮三路实现要点)）。
- **别造有状态模式**：翻转类动作（`C+Tab`，`ACTF_SINGLE_SHOT`，由 `IsSingleShotAct` / `StackRemove` 处理）不进重复/补齐，否则偶数次 = 没切。

### 窗口挪动（`winmove.c`）
- **按了 `C+Q` 没反应**有五种原因：前台是桌面/任务栏（按类名挡掉）、前台就是本程序自己（托盘菜单）、**前台是全屏窗口**（`WinIsFullscreen`，见下）、**已最大化且光标就在同一块屏**（什么都不用做，见上）、或者该程序命中 `[AutoDisable]`（整段不介入）。记录模式下会写两行 `[窗口]`：类名、光标、显示器/工作区、尺寸、请求落点、实际矩形、尝试次数；全屏那条会写 `全屏窗口不做移动`，同屏最大化那条会写 `不还原不挪`。
- **全屏窗口"挪跟没挪一样，只会抖动一下"**：那是 `SW_RESTORE` → `SetWindowPos` → `SW_MAXIMIZE` 三步跑完的结果 —— 挪到新位置又立刻铺满回去，用户只看得到一次重绘闪烁。判定（窗口矩形 == 显示器 `rcMonitor`）必须在 **`SW_RESTORE` 之前**，`C+Q` 与 Caps+左键拖动共用 `WinIsFullscreen`，否则会出现两边行为矛盾。
- **"要按两下才过去"**：落点改成"左上角对齐光标"之后已经不依赖窗口尺寸，所以现在只剩一种成因：**对方程序收到移动请求后又自己挪走**（带吸附/跟随行为的启动器、面板）。那里会**回读左上角**再补发（≤3 次），日志第二行会带"锚点未就位"。
- **别把"最大化"当普通窗口挪**：它的位置由系统按所在显示器算。必须先 `SW_RESTORE` 再挪、挪完 `SW_MAXIMIZE` 回去；而且要**确认回读一致（= 位置已生效）再最大化**，否则会铺回**原来**那块屏。
- **别把"全屏"当"最大化"拦**：两者判据不同 —— 全屏比的是 `rcMonitor`（整块显示器），最大化窗口的矩形是 `rcWork`（矮一个任务栏）。用 `rcWork` 当全屏判据会把普通最大化窗口一起误杀。
- **别用显示器全矩形算落点**：要用 `rcWork`，否则窗口会压到任务栏下面。（`rcMonitor` 在本模块的用途只有"全屏判定"这一个。）

### 拖拽窗口（`drag.c`）
- **拖不动 / 只对某些窗口生效 / 窗口比光标跑得快**：**先看启动基线里的"坐标空间"那一行**。
  显示"虚拟化(与钩子不一致)"= 主进程的 DPI 感知没生效 —— 钩子给物理坐标、本进程用虚拟坐标，
  于是 `WindowFromPoint` 指到别处、位移也按物理量算（见[坐标空间](#坐标空间为什么主进程必须声明-dpi-感知)）。
- **点一下就把最大化窗口缩小了**：那说明拖出阈值没生效（还原被提前发出）。
  看记录模式的 `[拖拽] 越过拖出阈值(20px)`；纯粹点一下应该看到
  `结束（未越过拖出阈值，窗口未动）`。
- **左键没被接管**：按顺序查 —— `[DragWindowBlacklist]`（类名）/ `[DragProcessBlacklist]`（进程名）、全屏（`WinIsFullscreen`）/最小化、桌面/任务栏/本程序自己的窗口、`[AutoDisable]` 或暂停。五类都原样透传。
- **全屏与 `C+Q` 必须同标准**：拖动的全屏判定不再自己写一遍，改调 `winmove.c` 的 `WinIsFullscreen` —— 两边各写一份时曾出现"拖动不让动、`C+Q` 却去动"。改动其中一边时另一边的测试（`test_chord` 场景 AE / AF 各有一条全屏用例）会一起红。
- **拖动一卡一卡 / 位置跳**：记录模式下看 `[拖拽]` 两行（开始/结束 + 拍数）；"最大化还原没等到"会直接放弃本次拖动（ 宁可不动也别挪错）。
- **`Caps+左键` 传给了目标程序**：只可能是 `[AutoDisable]` 命中或 `g_state.paused` —— 其它情况左键 down 都会被吞。

### 托盘气泡（main.c `TrayBalloon`）
- Windows 通知区**同一图标同时只显示一条气泡**；当前气泡还在时再发 `NIM_MODIFY + NIF_INFO` 会被**排队**（Win10/11 下被转成 toast、同来源摞进队列），要等前一条超时（约 10s）才弹——表现为"开始记录的气泡还挂着，按 `C+\`` 结束的气泡迟迟不出现"。
- **强制立即替换**：先发一条**空 `szInfo`** 把当前气泡收掉（取消排队），再发新内容。`NIF_REALTIME` 是反方向（不能立即就丢弃），**不能**用。纯应用内 API，不碰注册表/系统设置。
- **不自动消失**：`uTimeout = 0`（本 SDK 下唯一合法名；`uTimeoutOrVersion` 由系统填版本号，写它没有意义 —— 它在 Win2000 之后就不再是超时字段了）。本程序的气泡都是"结果通知"（钩子装上没有、日志写到哪份文件），看到 = 确认；尤其"记录结束"那条要支持点击，10 秒够不上一会儿才回来处理日志的人。
- **可点击**（`TrayBalloon` 第二参数 `clickPath`）：非空即表示这条气泡可点。做法是把路径存进 `g_balloonPath`，等托盘的 `uCallbackMessage`（本程序是 `WM_TOGGLE_TRAY`）送来 `NIN_BALLOONUSERCLICK` 时取出、执行"打开并选中"（复用 `folder.c` 的 `FolderRevealPath`）。
  · `NIN_BALLOONUSERCLICK = WM_USER + 5`，官方文档有定义，但**不要**顺手把同族的 `NIN_BALLOONTIMEOUT` / `NIN_BALLOONSHOW` / `NIN_BALLOONHIDE` 也接上：那几条只在 balloon 被**内联绘制**进通知区时才会送到 `uCallbackMessage`，走 toast 时系统根本不发 —— 依赖它们会写出"某些机器上有效"的代码。只有 `NIN_BALLOONUSERCLICK` 两条路径都可靠。
  · **点击与点图标必须分开**：`WM_TOGGLE_TRAY` 分支先判 `NIN_BALLOONUSERCLICK`，命中就走 `TrayBalloonClicked()` 并**直接 return**，不能再落到下面的 `WM_RBUTTONUP`/`WM_LBUTTONUP` 分支去弹托盘菜单 —— 气泡（尤其在 Win10/11 转成 toast 之后）离图标很远，把两件事接在一起会变成"点个通知，怎么跳出一个菜单"。
  · **一次点击只生效一次**：`TrayBalloonClicked` 先拷路径再清 `g_balloonPath`，重复点同一条不会再动作。
  · **旧图标的气泡作废**：`TrayRebuild` 里调 `TrayBalloonClearClick()`。explorer 重启后新实例不认旧通知（点了也没反应），宁可不动作，也不要"点了有反应但点错东西"。
  · `g_balloonPath` 只由主线程读写（`TrayBalloon` / `WM_TOGGLE_TRAY` / `TrayRebuild` 都跑在主线程），所以**不加锁**。
- **记录日志的起止提示音**（`RecBeep`）：开始 `SystemAsterisk`、结束 `SystemExclamation`，走 `PlaySoundW(SND_ALIAS | SND_ASYNC | SND_NODEFAULT)`。别名缺失（注册表被精简）时退回 `MessageBeep`。
  · 关键是**不能用 `MB_ICONHAND` 表示"结束"**：那正是系统给**严重错误 / UAC 提权**配的音，和"未按管理员运行时弹的提示"同源。记录是常开常关的操作，每次结束都响一声"出错了"，用户会去查一个并不存在的问题。
  · 用别名而不是硬编号：用户能在控制面板的声音方案里单独改，或在"无声"方案下安静下来（`MessageBeep` 在无声方案下同样是静音，行为一致）。
  · 声音依赖 `mmsystem.h` + **`winmm.lib`**：`build.bat` 与 `test\build_test.bat`（`test_chord.c` 包含 `main.c`）都加了它。
- `TrayHint`（悬停提示 `szInfo`/`szTip`）不受此限，改完立即生效。
- **单测里换掉托盘菜单**：`test/test_chord.c` 在 include `main.c` 之前 `#define CAPS_NO_TRAY_MENU`，`main.c` 里那段 `ExeDir → LaunchSettings → TrayShowMenu`（外加后面的 `SetMenuPauseText`）被整段门控掉，测试自己提供一个只记账的 `static void TrayShowMenu(void)` 接上 `WM_TOGGLE_TRAY` 的调用点 —— 真的 `TrackPopupMenu` 会阻塞弹窗，测试既不该弹也不该被挂住。
  · 门控必须覆盖**整条链**：那一段里每个函数的唯一调用者都在段内，只围最外面的 `TrayShowMenu` 会被 `/W4` 报一串 `C4505`（`ExeDir` / `LaunchSettings` / `SetMenuPauseText` 都浮出来）。
  · **不要**用 `#define` 给函数改名来"顶掉"生产定义：所有 TU 都按 `/TP` 当 C++ 编，同名 static 重定义是 `C2084`（已有主体），改名那条路走不通。门控只围定义、不围调用点，才是与本项目编译方式相容的做法（这也是["源码按 C++ 编译"](#源码按-c-编译tp)那一节说的 `C4505` 会浮出来的一个实例）。

### 配置（config.c）
- **改一个配置项要动八处**（常量 → `ConfigLoadFrom`（含钳制）→ `kTemplate` → `kUpgrades` → `ConfigGet*` / `ConfigSet*` → `GeneralValues()` → `settings.c` 的 `kFields` → README/本文；完整清单见下）。漏一处只静默不一致。改默认值务必全局搜数值（注释/模板/`kUpgrades`/测试断言里都可能写死）（详见[配置项的设计与新增清单](#配置项的设计与新增清单)）。

### COM / 跨进程
- **借来的接口指针绝不 Release**：曾把调用方 `FindDocElement` 传进来的元素也 `Release` → WPS 每次走失败路径、引用计数归零 → `c0000005`。只有 `AddRef` 过或规则上归你的才释放（详见[按词跳转](#按词跳转wordjump实现) 的"UIA 引用计数坑"）。
- **用 `src/comptr.h` 的 `ComPtr` 而不是手写 `Release`**：40 行最小 RAII 智能指针（不引 ATL / WRL）。ctor 语义是**接管**（不 AddRef，与 WRL 的 `Attach` 一致）；**只包"拥有的引用"** —— 借来的指针包进去就又变成上一条那个崩溃。`wps.c` 已全量使用；`nav.c` 仍是手写（`FindDocElement` 的 `chain[0]` 借 / 自有混在一起，改它要真机验证 UIA 与 WPS 两条路径）。
  > 注意：`nav.c` 里手写的 `IAccessibleText` vtable（文件头附近）**与引用计数无关** —— 那是因为 Windows SDK 不带 IA2 头文件，必须自己按官方 IDL 声明 vtable 布局。`ComPtr` / WIL 都解决不了它。
- **`SendMessageTimeout` 返回值 ≠ 窗口过程返回值**：必须经 `lpdwResult`（统一用 `SendMsg()`）。传 `NULL` 会拿到恒为 1 的状态值——曾导致 `WM_GETTEXTLENGTH` 恒等于 1、文本只读到一个字符（详见[按词跳转](#按词跳转wordjump实现) 的"跨进程消息坑"）。

### 命名约定（避免分叉）
- 激活键（`Alt/D`、`F`）属和弦语法、**不做配置项**；模式由 `keymap.c` 的 `MODE_*_KEYS_DEFAULT` 定义，引擎只问 `ModeDown(mode)`，不判具体键。
- **同一概念只留一份判据**：修饰判定统一走 `ModeDown()`（hook 与 chord 都用），不要再各写一套。
- 通用能力（COM 按名调用 `autodisp.c`、降权桥 `bridge.c`）与专用通道（`wps.c`、将来别的 COM 程序）分离；COM 接口声明放 `auto.h`（要 `<oaidl.h>`），**不塞进 `cap.h`**。

## 构建 / 测试 / CI

依赖 **MSVC x64**（Windows 10/11），工具链由 `build_env.bat` 统一定位：用 vswhere 探测 VS/MSVC/SDK 并显式设置 `PATH/INCLUDE/LIB`（不走 vvcvars64，避开它的注册表探测；批处理里含 `(x86)` 的路径不能内联展开，也无法出现在 `( )` 块 / FOR 集合里）。

### 源码按 C++ 编译（`/TP`）

所有 TU（含 `test\` 下的测试与诊断工具）都按 **C++** 编译，但**代码风格仍以 C 为主**，这是刻意的过渡态：

- **为什么切**：C++ 能逐文件带来这个项目真正需要的东西 —— 强类型（动作 / 模式 / 方向不再是一堆裸 `int`）、资源生命周期（COM 引用计数、句柄、临界区）、`std::string` / `std::vector` 替掉"手工算分配容量"（本项目已两次栽在这上面，见 `config.c` 的 `OutBuf` 注释）。一次重写风险太高，所以先把编译面切过去，再按模块换写法。
- **COM 的 C 接口桥**：`nav.c` / `autodisp.c` / `wps.c` 的 COM 代码是按 `p->lpVtbl->Method(p, ...)` 写的，而 C++ 下 SDK 默认给的是"带虚函数的 C++ 接口"。`src/cap.h` 顶部因此定义了 **`CINTERFACE` + `COBJMACROS`**，让 SDK 继续给出 C 形态的 vtable 结构体 —— 同一份源码在 C 与 C++ 下都能编过。独立诊断工具（`uiprobe.c` / `wspset.c`）不包含 `cap.h`，各自带一份同样的定义。**换完 COM 写法后这个块即可删除。**
- **`REFIID` / `REFCLSID` / `REFGUID` 在 C++ 下恒为引用类型**（与 `CINTERFACE` 无关，见 `guiddef.h`），所以传 IID 时写 `IID_XXX` 而不是 `&IID_XXX`；但 `CLSIDFromProgID(LPCLSID)` 这类**指针**参数的 API 仍要写 `&clsid` —— 同一个变量两处写法不同，别去"统一"（`wps.c` / `wspset.c` 各有一处对照）。
- **切到 C++ 会顺带暴露 C 前端不报的告警**：实测 `C4505`（内部链接的静态函数未被引用）会浮出来，那些是真正的死代码，按零告警基线删掉即可。
- **产物会变大**（实测 `245760` → `264192` 字节，同 toolchain 同源码）：C++ 前端会带进异常 / RTTI 相关的 CRT 代码。要判断"是不是同一份产物"看 SHA256，不要看体积。

> 排障两个常用工具：`bin\ilcheck.exe` 打印各进程完整性级别（"管理员运行附不上 WPS"就是靠它定性的）；`bin\lowrun.exe <exe> [args]` 借 `explorer.exe` 令牌以普通权限启动任意程序。二者在 CI 里只编译、不运行。

**CI（`.github/workflows/ci.yml`）**：push / PR 时在 `windows-latest` 依次执行——单测集成（`build_nav` + `build_test`）→ Debug CRT 堆越界守卫（`build_dbg`）→ 诊断工具构建 → 静态分析（`build_analyze`）→ 进程级检查（`restarttest`、`logsmoke`）→ WPS 通道编译 + 真机检查（无 WPS 自动跳过）→ `build.bat` 编译并上传 exe artifact。

所有构建（含 `build.bat`）统一 **`/W4`**，CI 里再跑一轮 `/analyze`：这两级都抓过真实缺陷（`act.c` 停止标志 Interlocked 混用、`config.c` "按 A 分配按 B 读"），代价只是编译时间。目前全项目 `/W4` + `/analyze` **零告警**，新增告警会立刻被看见而不是淹在已知噪音里。

## 可复现构建与跨机哈希差异

**这是正常的，且哈希"本来就不可能一样"**——除非做下面两件事。

**(1) 哈希：不加 `/Brepro` 时，同一台机器连续构建两次哈希都不同。** PE 头里有 `TimeDateStamp`（构建时刻）和 toolset 相关 `Rich` 头，另有链接器写入的 PDB GUID——每次构建都变（实测同机同源码两次构建大小同为 245760 字节、SHA256 却不同）。`build.bat` 现在带 **`/Brepro`**，得到"同 toolchain + 同源码 → 字节完全一致"的产物（要求 VS2019 16.6+ / MSVC 19.26+）。这样"CI 的产物是不是和我本地那份一样"才成为可回答的问题。

**(2) 大小：即使源码与参数完全相同，MSVC / Windows SDK 版本不同，产物大小也会不同。** 指令选择、内联策略、静态链接的 CRT（`/MT`）、SDK 头里 inline 实现，全随版本变化。实测 MSVC `14.44.35207` + SDK `10.0.26100.0` → 245760 字节。`build_env.bat` 用 `vswhere -latest`，所以 **CI runner 镜像升级会在全绿情况下悄悄换工具集**。现在：

- `build.bat` 与 CI 打印 `[ENV] VS=… MSVC=… SDK=…` 及产物的 size + SHA256（CI 写成 `BUILD-FINGERPRINT.txt` 随 artifact 上传）→ 两边一比就知道差在哪。
- 需要跨时间比对时钉住 VS 代次：`set CAPS_VSVER=[17.0,18.0)` 再构建。不钉是默认行为，钉住换来可比产物。

**顺带一个容易误判的点**：exe 的节按 512 字节对齐，几百字节的代码变化可能根本不体现在文件大小上（大小相同 ≠ 内容相同）。要判断是否同源看哈希；要判断工具链是否一致看 `[ENV]` 行。

> `bin` 下的 `*.obj` 是编译中间产物（已随 `*.log`、`*.exe` 一起被 `.gitignore` 忽略），可随时删除，构建会自动重新生成。
